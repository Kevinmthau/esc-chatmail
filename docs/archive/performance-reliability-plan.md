## Findings summary (verified at HEAD 02f3ebc)

### Sync / API

- **M0 (NEW, HIGH)**: Label reconciliation issues up to ~101 GETs on nearly every incremental sync — skipped only when history reported zero changes (IncrementalSyncOrchestrator.swift:212-218); `listMessages(query: last-24h, maxResults: 100)` then one `getMessageMetadata` per id at 10-way concurrency (SyncReconciliation.swift:553-574, 634-686, concurrency :518); `checkForMissedMessagesWithDiagnostics` additionally runs on **every** sync (ReconciliationPhase.swift:45). ~500 quota units per push-triggered sync; dwarfs H1's volume and is a primary 429 source feeding M3.
- **H1**: N+1 message fetch, one GET per message (MessageFetcher.swift:110-121 at concurrency 15; BackgroundMessageProcessor.swift:241-252 at concurrency **10**, correcting v1); Gmail multipart `/batch` never used (only `batchModify` exists). Deferred (C1).
- **M1**: History retry path (GmailAPIClient+History.swift:98-130) misses `credentialsRevoked` mapping — revoked refresh token loops in `tokenRefreshAndRetry` instead of `abortNoRetry`; 403 falls to retriable-classified `serverError`.
- **M2**: Three stacked layers per fetch — inner retry loop (GmailAPIClient.swift:174-339, up to 3 attempts, 120s budget), 15s `withTimeout` wrapper (MessageFetcher.swift:114,162) that amputates inner backoff (URLSession per-request timeout is forced ≥30s at GmailAPIClient.swift:87, so a single slow request already exceeds it), and MessageFetcher's own 3-attempt loop (:256-291) — up to 12 HTTP attempts per message with no inner backoff ever completing.
- **M3**: `RateLimitTracker.recordSuccess()` credits 30s per 200 (GmailAPIClient.swift:31-36); at 15-way concurrency, 4 interleaved successes wipe a fully-tripped breaker — designed for a serial client.
- **M5**: `refreshSendAsAliases` network call every incremental sync (IncrementalSyncOrchestrator.swift:128,520-541).
- **M6**: 401 refresh consumes a retry attempt; 401 on the final attempt exits via `throw lastError ?? URLError(.unknown)` (GmailAPIClient.swift:267→338; same bug in +History.swift:107→157) **even after a successful refresh**. `URLError(.unknown)` is non-retriable per `MessageFetcher.isRetriableError` → message lands in `permanentlyFailedIds`. Related pre-existing bug: History's 429 branch (:88-96) has no final-attempt guard — sleeps the full Retry-After, then throws `URLError(.unknown)`.
- **L2**: Keychain read per request (expiry not cached in memory), plus a per-request MainActor hop (TokenManager.swift:123).
- **L3**: Sequential profile/sendAs calls at initial-sync start (InitialSyncOrchestrator.swift:230-239).
