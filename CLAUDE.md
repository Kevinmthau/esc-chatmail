## Layout

- `esc-chatmail/` is the app target; `Services/` holds nearly all logic, with Sync, Send, Caching, HTMLContent/HTMLSanitization, EmailDOM (SwiftSoup) and Chat the dense areas.
- Entity classes: `Services/CoreData/ManagedObjects.swift` (`@objc` class decls) + `Services/Models/<Entity>+Extensions.swift` (`@NSManaged` props, helpers). Exceptions, whose `@NSManaged` props are declared in `ManagedObjects.swift` itself: `ChatReplyDraft` and `OutboundSendMutationRecord` (neither has a `+Extensions` file) and `Attachment.replyDraft`. Adding an attribute means editing the versioned `.xcdatamodel` **and** the file holding that entity's `@NSManaged` props.
- `esc-chatmail/Models/` holds the versioned schema (`esc-chatmail/Models/CoreData/ESCChatmail.xcdatamodeld`, current version `ESCChatmail 6.xcdatamodel`; a schema change is a new version directory plus the `.xccurrentversion` bump, never an edit to a shipped version, whose hashes on-device stores carry) plus a legacy grab-bag of value types; entity *class* code is not there.
- Test directories broadly track `Services/` subsystem names but are not a strict mirror; shared fakes live in `esc-chatmailTests/TestSupport/` (`Mocks/`, `Builders/`, `TestCoreDataStack.swift`, `FakeSyncClock.swift`).
- App and unit-test targets use filesystem-synchronized groups: new `.swift` files are picked up automatically. Never hand-edit `project.pbxproj`.
- `web/` is an independent React/Vite/Dexie PWA in no Xcode target. Its only contract with iOS is the golden corpus, imported live via the `@fixtures` alias — editing `esc-chatmailTests/TestSupport/Fixtures/**` triggers web CI.

## Account-generation boundary (break this and data leaks across accounts)

Every account-scoped subsystem is fenced by an admission flag plus a monotonic generation — roughly two dozen participants today; enumerate them with `grep -rn 'func reopenAccountWork\|func reopenAdmission' esc-chatmail/` rather than trusting a number here.

- **All orchestration lives in `AuthSession`** (`Services/Security/AuthSession.swift`). Four entry paths (`restorePreviousSignIn`, `signIn`, `signOut`, `signOutAndDisconnect`) serialize on a FIFO auth-transition gate (`beginAuthenticationTransition`/`endAuthenticationTransition`); the crash-resume pair (`resumeInterruptedAccountRemovalIfNeeded` / `resumeInterruptedCredentialCleanupIfNeeded`) deliberately takes no gate of its own — it runs inside `restorePreviousSignIn`'s ownership and must never gain another caller. Like every path, it signs Google out through the injected `signOutGoogleSession`, never `GIDSignIn.sharedInstance.signOut()` (whose only call in `AuthSession.swift` is that seam's default, pinned by `testGoogleSDKSignOut_isCalledOnlyFromTheSeamDefault`): called directly, a Mac test host would delete the installed MushMail's Google session (inferred from the shared keychain group, not measured). All six then follow one fixed order: `outboundTaskRegistry.closeAdmission()` → `syncRunCoordinator.beginQuiescence()` → `cancelAndAwaitAll()` → `cleanupDownloads()` → destructive cleanup → reopen → `endQuiescence()` → only then publish authenticated UI. Gate-vs-close ordering differs by direction, deliberately: `signOut`/`signOutAndDisconnect` persist the durable reset marker and call `closeAdmission()` synchronously **before their first await** (so a queued sign-out's intent survives even while an earlier transition owns the gate), then wait on the gate; `signIn`/`restorePreviousSignIn` take the gate **first** and close admission once they own it — a queued sign-out supersedes them via `isAccountRemovalRequested` re-checks at the destructive-cleanup and reopen checkpoints (**not** after every await: the seam between `endQuiescence()` and publishing authenticated UI has no re-check, so a sign-out landing there sees a flash of authenticated UI that it immediately tears down — accepted as cosmetic). The gate has no reentrancy detection and gate waits are uncancellable (`withCheckedContinuation`): never start a second transition from inside one.
- A new participant must be wired into `AuthSession`'s six injectable closures (`cleanupHTMLContent` / `reopenHTMLContent` / `cleanupDownloads` / `reopenDownloads` / `resetPendingActionRetryState` / `pendingActionAuthenticationDidRecover`), or into `HTMLContentLoader.closeAccountWorkAndClearCaches()`'s fan-out. Otherwise it never closes. Any new AuthSession path that publishes an authenticated session must call `pendingActionAuthenticationDidRecover` — the pending-action queue's revoked-credential park is released only there, and a forgotten hook parks the queue until process restart. Plain account-scoped state with no work to drain (`SyncEngine`'s full-disk backoff and banner) resets through `resetSyncStorageState`, called beside `resetPendingActionRetryState` on every path that calls it.
- Participant contract (duck-typed; there is no shared protocol): `private var acceptsAccountWork`, `private var accountGeneration: UInt64`, `captureAccountGeneration() -> XAccountGeneration?` (nil while closed), `isAccountGenerationCurrent(_:)`, a close method, `reopenAccountWork()`. Define your own nominal token struct — never pass raw integers or another subsystem's token. `MessageBubbleHTMLAnalysisCache` is the smallest complete example.
- Closing must **drain**, not just flip a flag: cancel and `await` every in-flight task before clearing storage. Producer closures retain old-account content even when their final write is generation-rejected. Naming encodes it (`...AndAwait`, `...AndClear`). Reopen guards refuse while work is outstanding, so a leaked task silently keeps the subsystem closed for the next account.
- Caller contract: capture tokens once up front (bail if any capture returns nil), re-validate after **every** await before using or storing a result, and pass `expectedAccountGeneration:` down into async writes. Multi-participant callers build a composite context (`MessageBubbleLoader.captureAccountWorkContext()`).
- Reopen is all-or-none: `AuthSession.reopenAccountWork(after:)` rolls back downloads and HTML if a later reopen step refuses. Anything but `.reopened` means do not publish an authenticated session, and the three refusal cases are **not** interchangeable — `.transientFailure` (a reopen step threw; retry with the same credentials), `.latchedRefusal` (old-account work still outstanding — a refused download reopen or an undrained outbound send reservation; this transition cannot publish and repeating it is not expected to clear the latch; only the outbound cause proves no superseding transition exists — the download cause cannot check, and a sign-out queued mid-reopen behind it converges benignly with the restore's credential discard), `.supersededByAccountRemoval` (a queued sign-out owns the teardown, including its own credential cleanup). `OutboundTaskRegistry.reopenAdmission(after:)` distinguishes those two refusals itself and deliberately reports supersession before undrained sends when both hold — a latched verdict on a stale transition would route a restore into discarding credentials the queued sign-out owns. `AuthRestoreReopenPolicy.restoreDispositionAfterReopen(_:)` owns the outcome→credential-disposition mapping for the restore path; never clear credentials on a cause it maps to `.retryKeepingCredentials`. `reopenPreSignInAccountWork` is deliberately *not* all-or-none: its caller cannot unpublish the session it is restoring, so a refused download reopen degrades (log only) and outbound admission still reopens; an undrained-sends outbound refusal likewise degrades (send latch only), and only genuine supersession rolls back. Reopen must also recreate directories cleanup deleted (`AttachmentPaths.setupDirectories()`, Messages dir, preview cache dir).
- Restore and sign-in additionally gate on `prepareLocalStoreForAuthenticatedAccount(_:)`, held under the account-transition lease: the app owns **one** account-wide store and conversations carry no account predicate, so a matching `Account` row is not sufficient (any other surviving row forces a reset) and an absent row is safe only when the mailbox store *and* the canonical HTML directory are genuinely empty. One exception, and only this one: after a recovery reset of the store (the ladder's corrupt-store reset or the launch screen's confirmed Reset Mailbox, both marked by `StoreRecoveryResetMarker` before the removal), an empty store beside files, with no row of any entity and the keychain still naming the account being prepared, has its body and attachment files removed and nothing else (`removeMailboxFilesLeftByStoreRecovery`): no credential cleanup, no second store reset (which removes every backup, the reset's own included) and no move of the mailbox start. Any doubt (no marker, a row, an unreadable or different keychain account) is the full cleanup, and every decision of the gate and every completed account cleanup clears the marker. Never publish authenticated UI before it returns; failure maps to `AuthError.localAccountIsolationFailed`.
- `TokenManager` runs its **own** sign-out generation, separate from these fences. `cacheLock` guards the cached token pair, the epoch, **and** both writers' keychain writes/deletes, so `saveTokens`/`clearTokens` can never interleave keychain operations; **both** `clearTokens` and ungated `saveTokens` (sign-in/restore via `persistSessionForBackgroundAccess`) bump the epoch inside that section — any future ungated `saveTokens` call site therefore silently cancels in-flight refreshes, by design. Any new token-producing path must snapshot the epoch *before* its unserialized keychain read or network call, publish only via `setCachedToken(_:ifEpochMatches:)`, and after the MainActor hop re-check that the epoch still matches **and** the cached token equals the one being published before assigning `authSession.accessToken` — a bare `cachedToken() != nil` is insufficient now that ungated saves bump the epoch, because a replacement account's freshly cached token would pass it and a retired publish would overwrite the replacement's session state. Refresh single-flighting is `TokenRefreshCoordinator`, keyed on that epoch: a refresh whose generation was retired throws `CancellationError` rather than returning a token, overwriting replacement tokens, or publishing a revocation verdict into the replacement session — callers must not expect a token-once grace delivery after sign-out.
- `CacheCoordinator` captures the generation on the **posting** context's queue inside the didSave publisher, before `.receive(on: .main)`. Any new notification-driven invalidation must capture at post time, not delivery time. The deleted rows' values are captured there too (`invalidationPlan(forSave:)`), from the instances under `NSDeletedObjectsKey`, and only values cross to main. Never resolve a deleted object's ID after the save: it resolves to an object with a nil `id`, nil paths and no attachments, which is why no file of a deleted message was removed before 2026-11-17 and every deleted Person cleared the whole `PersonCache`. Inside that notification a deleted message's `attachments` is already empty, so an attachment's paths are read off the deleted attachment itself, and nothing there may fire a fault (`storedString`). The files are removed later, off the main actor, by the coordinator's two removers (`HTMLContentHandler.deleteHTML(forDeleted:…)`, `AttachmentCacheActor.deleteFiles(at:…)`), and each asks two things first (`DeletedRowFileReclamation`): that no stored row names the file, and that the file was not written after the delete. The same Gmail message can be stored again under the same file name before the removal runs (taken out of Trash, then synced), and its body is written before its row is saved, so neither question covers the other's case. A read of the store that fails removes nothing. The body check asks the store before the HTML boundary's lock is taken, never with it held: every HTML read and write and every context's save notification take that lock, and the file's date, read under it just before the unlink, is what covers a body written after the answer. An attachment file stored under an ID the app made (`local_`: what the user added, a forward's copy, the preview of either) is never removed with its row (`DeletedRowFileReclamation.isRemovedWithItsRow`) and is left to the orphan sweep: it cannot be downloaded again, only the sweep knows the compose leases, and the echo's replacement of an optimistic send keeps those files on purpose for a Quick Look that has one open. Never route a deferred removal through `deleteHTML(for:bodyStorageURI:)` or `deleteFile(at:)`, which ask neither. A `CacheCoordinator` a test builds takes `fileReclamation:` (`.asking` a store of the test's), because the default asks `CoreDataStack.shared`; `CacheCoordinatorDeletedRowCaptureTests` (a SQLite store, where a deleted row is really gone) and `DeletedRowFileRemovalTests` pin this.
- Interactive local mutations (mark read, pending actions) use the **non-exclusive** lease: `makeAccountWorkRequest()` → `acquireAccountWorkLease(kind:for:)` → work → `isActiveRun(_:)` re-check after each suspension → `endRun(_:)`. A lease holder must **never** wait on the exclusive boundary (`waitUntilIdle`/`beginRun`/`acquireRun`) before releasing — teardown drains leases, so that deadlocks. `acquireAccountWorkLease` deliberately ignores `Task.isCancelled`.
- A launch restore that cannot reach Google (`isConnectivityRestoreError`: offline, a timeout, Google's token endpoint failing), cannot read GoogleSignIn's keychain item while the app's keychain names an account, or fails a reopen with `.transientFailure` **holds** the account (`AuthSession.heldAccount`, `HeldAccount`): `ContentView` shows `HeldAccountView` (the mail is still on the device, Try Again, Sign In Again with the held address as hint) instead of the first-run `SignInView`, and `LaunchRestoreRetryCoordinator` runs `AppStartupBootstrap.restoreAuthenticationIfNeeded()` again on Try Again, on the path's return (`OutboundNetworkPathMonitor`, after a 2 s settle), after a 15 s doubling to 5 min backoff, on iOS `.active` and on Mac activation and wake; it pauses in the iOS background and for Mac sleep (architecture review 2026-11, item 5). A hold is not a session: `isAuthenticated` and `canAccessMailbox` stay false, so nothing syncs, arms or recovers pending actions, and only a real publish calls `pendingActionAuthenticationDidRecover`. Revocation (`isCredentialInvalidatingRestoreError`: GID -4, invalid_grant) still clears the session and ends the hold; any other error keeps the credentials but is not held or retried (the sign-in screen, as before), because asking again cannot mend it. A restore that cannot read a sign-out marker decides nothing and keeps an existing hold (`keepsExistingHold`). The hold is decided only where `restorePreviousSignIn()` ends (`concludeLaunchRestoreHold`, which refuses while a sign-out is registered) and cleared by `publishAuthenticatedSession`, `clearAuthState` and `registerAccountRemovalRequest` (neither sign-out path calls `clearAuthState`). A retry is always the bootstrap's single-flight restore from outside any transition, never `restorePreviousSignIn()` directly and never from a run or lease holder. The restore's deadline is on AppAuth's transport (`GoogleAuthTransport`: 15 s request, 30 s resource per token request, installed in `configureGoogleSignIn`; a restore with a current SDK user makes two), never a timeout around its `withCheckedContinuation`: GoogleSignIn has one slot for the flow in progress, and a wait that ended early released the gate to a sign-in whose completion the restore then consumed, leaving an uncancellable gate wait stuck. Reading stored mail while held (a seventh publish path) is an open decision, not a gap. `AuthSessionHeldAccountTests`, `LaunchRestoreRetryCoordinatorTests`, `LaunchRestoreRetryPolicyTests`, `GoogleAuthTransportTests` and `LaunchRestoreRetrySourceTests` pin this; nothing of it has been seen on a device.
- The pending-action queue is strictly oldest-first, and a transient failure (5xx, rate limit, timeout, a transport error) spends one unit of the head's budget and ends the run (`PendingActionRunStopReason.transientFailure`). The wait is the manager's fourth bounded timer (`scheduleTransientRetry`: 60 s doubling to 15 min, at least Gmail's Retry-After), out of the run, so sync can take the boundary meanwhile. The doubling belongs to one row: it restarts when a run abandons the head or a different row fails. The banner's Retry clears the timer (`resetTransientRetryBackoff`): the user asked for the queue now. A wait whose wall-clock deadline has passed no longer gates (`transientRetryGateIsClosed`), because the sleep behind it may not advance while the device sleeps. A failure after which the network monitor reads offline spends nothing and arms no timer (`.offline`): the reconnect edge resumes the queue, which the timer would refuse. A run that finds no path at all is `.offline` too, never `.completed`, which resets every backoff for a run in which nothing was sent. Label reconciliation's shield leaves out star and unstar, which change neither INBOX nor UNREAD; it used to sleep 2 to 30 s inside the run and go again, and a minute of 5xx abandoned the head and then each row behind it. That timer is a gate like the authentication and quota ones: `scheduleProcessing`, `processAllPendingActions`, both outcome switches, `currentOutcome`'s stale mapping, `resetRetryStateForAccountTransition` and `stopMonitoring` all name it, and a new gate site must too. Label reconciliation leaves alone a message a live action (`pending`, `processing`, `failed`) still has to change in Gmail (`PendingActionTargets.liveTargetMessageIDs`), whatever its 30-minute marker says; a failed read of the actions repairs nothing and makes the pass incomplete. History label processing keeps the age check alone, because a history item it skips is lost as the cursor advances.
- Add boundary regression tests next to `AuthSessionTests` / `HTMLContentAccountBoundaryTests`; the standard shape is "stale generation is rejected after reopen".

## Sync cursor and staging invariants

`SyncEngine` is a facade over `InitialSyncOrchestrator` / `IncrementalSyncOrchestrator`, gated by `SyncRunCoordinator` (single-flight).

- **Nothing but the orchestrator's own save points may save the sync context.** `SyncFailureTracker`, both checkpoint stores, and `AccountPersister.setAccountHistoryId` stage into the caller's context so the failure ledger, the durable counter, the continuation token, and the Account cursor commit or die together.
- Advance the Account `historyId` only when `planHistoryAdvance` returned `shouldAdvance` **and** the history slice is terminal (`nextPageToken == nil`). A truncated slice stages the continuation token and leaves the cursor frozen; a non-advancing slice moves neither.
- Apply `SyncFailureTracker` success-side effects only via `commit(_:)` **after** the final save succeeded; discard the plan on save failure. Never call `recordSuccess()`/`reset()` inside a run.
- Account-scoped aborts (`APIError.isAccountScopedSyncAbort`: auth, revoked credentials, quota) are run-level: put the IDs in **no** failure bucket, stop issuing requests, rethrow so nothing commits.
- Every attempted ID lands in exactly one `MessagePersistDisposition` bucket (persisted / excluded / unprocessable / failed). Only `.failed` and fetch failures freeze the cursor; 404s and deliberate exclusions must not.
- `MessageProcessor.processGmailMessage` encodes the body-materialization contract in *whether it throws*: a thrown error means content could not be fully materialized and the message **must not be persisted as-is** — callers map it to a blocking per-message failure (or a run abort for account-scoped errors) so the cursor cannot advance past a silently body-less row. Deterministic per-part failures (404, undecodable response) deliberately do **not** throw, because retrying cannot materialize the part; the best-effort embedded-HTML salvage probe never throws either (except account-scoped failures and cancellation). Classify any new body/attachment error into one of those three buckets explicitly.
- A message's body is read by one walk, `MIMEBodyExtractor` (ported rule for rule by `web/src/mime/mimeBody.ts`), which sync (`MessageProcessor.extractContent`) and recovery (`HTMLContentRecoveryService`, before its scoring) both call, so a recovered body is the stored one. It keeps the first non-blank leaf of each kind, and in a multipart/mixed it joins a text leaf that directly follows an `inline`-disposition file to the leaf of its kind the same multipart/mixed gave the body: the words after a photo iPhone Mail placed mid-message. Three things fail silently. A continuation is fetched through the caller's `decodedBody`, so in sync it throws on a transient failure like any body part; never wrap it in `try?`. Nothing stands in for the file in the stored HTML, which the preview and the rich-content verdict read, and no version is bumped: a row's body heals only when it is fetched again. And a text/html or text/plain part with no filename and no `attachment` disposition is never an attachment row (`extractAttachments`, web's `isServerAttachmentPart`), though Gmail serves a large one by attachmentId; `hasAttachments` still counts it. A row stored earlier keeps such an attachment row, refetched or not: the update path only adds attachment rows, and Gmail's attachmentIds are no key to match one for removal. `MessageProcessorSplitBodyTests` and `mimeBody.test.ts` pin this. No real split message has been captured from Gmail: the fixtures are built from the review's description of iPhone and Apple Mail.
- Cancellation always propagates as a thrown error and is never recorded as a per-message verdict — a partial partition would look like a clean batch.
- A failed Core Data read is never "absent"/"empty": `planHistoryAdvance` returns `.held` when the ledger is unreadable even on an otherwise clean run; lookup failures return `.lookupFailed`/`.failed` rather than creating duplicates or advancing.
- `recordFailure` **replaces** the deferred set and must never truncate; a staging failure latches `deferredStagingFailed`, which blocks the escape hatch.
- Ledger states have different retry owners: `deferred` rows are retried by the normal re-scan (excluded from the drain); `abandoned` rows only by the drain, which alone owns `retryCount`. Drain failures must never influence cursor advancement. The drain query's `state == nil` / `nextRetryAt == nil` disjuncts are load-bearing on SQLite.
- An initial sync or history recovery that dies part-way is resumed at its next page (scalability review step 8). Each page's completion stages `PagedSyncProgress` (next page token, the first attempt's pre-scan watermark, the cumulative failures and resolved ledger IDs) into the window's `SyncWindowCheckpoint` row, inside that page's save and never apart from it. A resumed run must add the earlier attempts' failures to its own before the completion retry and `planHistoryAdvance` (`PagedSyncProgress.merging(into:)`), or a clean tail advances past a message never stored, and must advance to the stored watermark, never its own profile's: the history from the first watermark is what covers mail that arrived and labels that changed after the earlier pages were listed. A listing older than `SyncConfig.pagedSyncResumeMaxAge` lists its window again from page 1. A held completion stages the window alone (dropping the progress) in its final save; only the advancing save deletes the row. An advance records the listing's start as `lastSuccessfulSyncTime`, never the time it finished (`SyncFailureTracker.commit(_:listingStartedAt:)`): the cursor is that listing's watermark, and recovery's and reconciliation's windows are measured back from that time, so a resumed run that recorded its end left the mail of the days between its attempts to the watermark's history alone. The stored page token is given up once, and the listing starts again from page 1, wherever trusting it could be wrong (`MessageIDPageStream.forEachPage`): any deterministic refusal of it (`refusesStoredPageToken`: a 4xx that is not account-scoped or a rate limit, never only a 400), and a first page that comes back empty with no next token, which an expired token answered that way would make a clean end. Transient and account-scoped errors propagate. How Gmail answers a stale `messages.list` token, and whether a days-old token is a position that trashed mail shifts, has not been measured.
- An app refresh (`BackgroundMailboxSyncBudget.allowsDeferrableWork == false`) runs the history slice and the missed-message list call only: no abandoned drain, no label reconciliation (and no reconciliation time written, so it stays due), and the missed IDs it finds go to `SyncConfig.deferredMissedMessageIdsKey` for the next larger sync. That sync settles them only after its save (`SyncReconciliation.settleMissedMessageFetches`): it forgets those now stored or gone and keeps every missed ID whose fetch or persistence failed, its own check's included, because no later check lists them (each lists after the last sync less five minutes, and the last sync is now this one); an ID is dropped after `SyncConfig.maxDeferredMissedMessageFetchAttempts` failures, counted at most one per `deferredMissedMessageFailureSpacing` (15 minutes), because a foreground sync runs every minute and five minutes of 5xx must not drop it. Nor does an app refresh wait out a rate limit (`MessageFetchWaitBudget.appRefresh`, a task-local `performSync` sets): a rate-limited pass is not retried and no GET is sent while the pacer is paused (not even for its one-second default after a 429 with no Retry-After, which sent a sustained limit's GETs one a second), so the refused IDs hold the cursor and the slice saves what it fetched, where the 50-second ladder expired the task before its save. The key is account data, cleared in `clearAccountScopedSyncDefaults`.
- Every message GET of `MessageFetcher`, label reconciliation's metadata GETs included (`getMessageMetadata`), goes through its `MessageFetchPacer` (token bucket, AIMD concurrency, Retry-After pause; a `Retry-After` of zero or less is no Retry-After, or one burst of 429s halves the concurrency to 1), and a rate-limited pass retries on `MessageFetcher.rateLimitedRetryDelays` unless the run's `MessageFetchWaitBudget` says otherwise. Never route the fetcher's single-attempt 429s into `GmailAPIClient`'s `RateLimitTracker`: concurrent refusals nobody waited on would trip its breaker. The metadata GETs keep the client's own retries, so only the 429 they finally throw reaches the pacer. A metadata GET takes a token and honours the pause but not the AIMD concurrency limit, so a caller that starts many at once (`HistoryRecoveryRepair.askGmail`) is held to the bucket's burst, not to the halved concurrency. In an app refresh a GET the wait budget refuses is a fetch failure like any other: it holds the cursor and counts toward `maxConsecutiveSyncFailures`, so a run of rate-limited refreshes can trip the escape hatch and hand those IDs to the abandoned drain, which retries them.
- A history recovery lists only mail after its window and outside Spam and Trash, so the save that advances its cursor also owes a repair of the rows it did not visit (`HistoryRecoveryRepairCheckpointStore.stageOwed`, never staged by a held recovery). Each later incremental run that may do expensive work, and whose history slice was terminal and clean (as for the delivery-unknown probe), plans one batch of it (`HistoryRecoveryRepair`, after the reconciliation phase): the newest 250 stored rows before the owed bound, three listings over their span, and a `format=metadata` request for each row the listings contradict, never more than 100. Only Gmail's answer for a row changes it: a 404 or a Trash/Spam/Draft label removes it, else it takes Gmail's INBOX and UNREAD. The plan is applied inside the final save's rollup block, with its conversations added to the block's turns and rollups, and its progress is staged there after the application, into the same save: a row `apply` left alone because a user's action was queued meanwhile keeps the bound above it (`HistoryRecoveryRepairPolicy.progressAfterApply`). Both batch fetches are newest first, so the request budget goes to the newest candidates. Never ask about or change the user's own unsent row (`OutboundSendDeliveryState.localOptimisticMessageID`) or a ledger row, which the bound passes. A row with a fresh local change, and every message a live pending action still has to change (`PendingActionTargets.liveTargetMessageIDs`, never a re-derived `messageId`/`conversationId` match, which misses a conversation action's payload after a merge), waits: not asked this run, and the bound stays above it (`HistoryRecoveryRepair.Exclusions`). Both are asked again when applying. Cancellation and account-scoped failures rethrow and end the run; a failed listing keeps the batch owed, and one too long to read skips the batch; an unanswered row stays owed with everything older (`HistoryRecoveryRepairPolicy.nextUpperBound`), and an unreadable answer (`decodingError` only: `invalidData` is every 4xx but 403 and 404, transient ones included) leaves the row as it is. After `HistoryRecoveryRepairPolicy.maximumRunsWithoutProgress` runs in a row that leave the bound in place, it steps past what holds it (`progressAfterStall`: the one row, or a failed batch), so no row stops the repair for good. The owed bound starts at `.distantFuture`, never the device's clock. Keep the bound a `Date`: as seconds since 1970 it round-trips a hair later than the stored row, and the batch cut at that row never finishes. Metadata never goes to `saveMessages`. The batch fetch has a plan test in `ScaleQueryPlanTests`.
- Background (BGTask) sync uses the same model-v3 executor and cursor/checkpoint rules as foreground sync. `BackgroundSyncManager` owns bootstrap/auth admission, expiration propagation, and retry scheduling; it must not write cursors independently. Keep `BackgroundSyncStateManager.clearContinuationState(in:)` at upgrade and account teardown boundaries to delete checkpoints left by the retired delta writer.
- The incremental path keeps its `UserDefaults` state (`lastSuccessfulSyncTime`, `installTimestamp`, `lastReconciliationTime`, the missed-message cursor) in an injected store, `.standard` by default: `IncrementalSyncOrchestrator(defaults:)`, which hands it to `ReconciliationPhase` and `SyncTimeCalculator`, `SyncReconciliation(defaults:)` and `SyncFailureTracker(defaults:)`. All three must be given the same store, because the tracker writes the last-sync time that the orchestrator's recovery and the reconciliation window read. `InitialSyncOrchestrator` still reads `.standard` directly.
- Every Gmail `after:` floor is measured against `ServerTimeSource.conservativeNow()`, the earlier of the device's time and Gmail's, and `lastSuccessfulSyncTime` is stamped with it, or with a paged listing's start moved a `deviceClockLead()` earlier where that is earlier still (`SyncFailureTracker.recordResolvedProgress`): a device clock set ahead by hand stamped a time Gmail had not reached, and the history recovery after an expiry skipped the mail between for good. Gmail's time is `ServerClockEstimate`, in memory only, fed from the `Date` header of a 2xx response to a request that may be retransmitted (`GmailAPIClient.performRetryingRequest`): never messages.send, where nothing may read, throw on or reclassify anything for it. The stored last-sync time and mailbox start are read as no later than that now (`SyncTimeCalculator.clampedToNow`), the last-sync time a further `deviceClockLead()` earlier (a stamp an earlier build wrote with the clock still ahead, which a clamp to now no longer reaches days later), and the mailbox start as no later than the last-sync time (a sync always follows a move of the start, so a later start was written by a clock that was ahead; this holds because every path that empties the mailbox clears the last-sync time, and a new path that moves the start over a kept one must clear it too). Not covered: the mailbox start is still written with the device's clock and gets no lead correction, so a first initial sync that runs later than the clock's lead after the sign-in, or recovery's install branch, still starts that lead late. Gmail's time is believed only within `ServerClockEstimate.maximumPlausibleSkew` (30 days) of the device's, because "earlier" alone puts no bound on how much earlier one broken `Date` header could make every floor. Each of these can only move a floor earlier: recovery stays uncapped and frozen at its first attempt, and nothing may cap it to now. The tracker, both orchestrators and `SyncReconciliation` take the same source (`serverTime:`), as they take the same defaults; `SyncClock` is not it and stays the pacing clock.
- `installTimestamp` is the mailbox's start, not the install's (`SyncConfig.mailboxStartTimestampKey`): the floor of the initial sync, history recovery and reconciliation. A sign-out wipes the mailbox and the sign-in after it starts fresh from the sign-in, bringing no earlier mail back (Kevin, 2026-11-16). So `AuthSession` moves the start to now in two places and no others: `performDurableLocalCleanup`, once the store and files are gone, and `prepareLocalStoreForAuthenticatedAccount` when an interactive sign-in (`entry: .interactiveSignIn`) finds the store empty. Never move it over a retained store (`clearFailedGoogleSession`, a same-account sign-in): it is history recovery's floor, and the mail between the old start and now would be skipped. Never move it for a restored session that finds the store empty either: that is the launch after a sign-in whose first sync saved nothing. `clearAccountScopedSyncDefaults` also removes the missed-message cursor, which holds the old window's `after:` query for a day and was resumed by the next sign-in's first reconciliation. A store reset with no sign-out (the Core Data recovery ladder, or the launch screen's Reset Mailbox) moves nothing and re-lists up to `initialSyncMaxWindow`: the isolation gate's restore after it removes the orphaned files without the full cleanup (`StoreRecoveryResetMarker`), which would move the start.
- A sign-out also removes what the mailbox left outside the store, the message bodies and the attachment folders (`AuthSession.clearMailDerivedCaches`, run by the default `deleteAttachmentFiles` closure and by the fresh-install cleanup): `Documents/Avatars`, the remote-image cache (`EnhancedImageCache`, `Caches/ImageCache`), `URLCache.shared`, the web views' default data store, and on the Mac the vCard last handed to Contacts. It is best effort and has its own Mac tripwire operation. The web views' data is removed through `withSoftTimeout` and never awaited bare: nothing bounds WebKit's answer, and the durable cleanup awaits it with the auth-transition gate held and its reset marker still to hand over (`testClearWebViewData_webKitRemoval_isAwaitedThroughASoftTimeout`). `MailDerivedCacheCleanupTests` runs the function on iOS and pins its two call sites from source, because every test's `AuthSession` and `FreshInstallHandler` inject their own cleanup; keep that suite out of `Mac.xctestplan`, where the stores it empties are the real container's. The image cache is not a participant of the account boundary: a load in flight can write one file after the cleanup. A new on-disk store of mail-derived data must be added there or to a participant's close. Left in the preferences on purpose: the launch-repair checkpoints (message IDs and participant hashes; see the note in `ConversationLaunchRepairCoordinator`) and the contact-link map, which is the device's Contacts.
- The cleanup a sign-out awaits unlinks none of the mailbox's files. `Messages`, `Attachments`, `Previews` and the legacy attachment cache are each renamed to a tombstone beside them (`Messages.deleting-<UUID>`, `RetiredAccountDirectory.takeOutOfUse`), which costs the same for three files as for 150,000, and a detached background task removes the tombstone afterwards; every launch removes the ones an earlier run left (`sweepLeftovers`, from `initializeApp`). `HTMLContentHandler.deleteAllHTMLFromClosedAccount`, `AuthSession.deleteAttachmentFilesFromDisk` and the fresh-install cleanup keep their names and their Mac tripwire guards, and the renames run where the unlinks ran, after the writers are closed and drained. Five things fail silently. A tombstone is a sibling of the directory, never inside it, and is not counted as another account's files: `AccountScopedMailboxFileInspector.hasStoredFiles` and `HTMLContentHandler.hasStoredHTMLFiles` look in the live directories only, and counting a tombstone makes the sign-in after a sign-out reset the store a second time. Until the reopen there is no `Messages`, `Attachments` or `Previews` directory at all, so every reopen path must still make them (`reopenAccountWork`, `AttachmentPaths.setupDirectories()`). The removal is not a participant of the account boundary and is never awaited or drained: await it and the unlinks are back on the auth-transition gate. `sweepLeftovers` returns its task for its test alone; the launch discards it. It may touch nothing but a tombstone, which is what makes that safe, so `RetiredAccountDirectory.remove` refuses any URL not named as one; keep that guard. And a directory of account files that a sign-out removes whole goes through `takeOutOfUse` and into `RetiredAccountDirectory.accountDirectories()`, or a tombstone of it is never swept after a kill. `RetiredAccountDirectoryTests` and `AuthSessionTests`' sign-out over real files pin this by structure (the awaited cleanup returns with every file still on disk); nothing was timed, and no sign-out of a large mailbox has been made on a device.
- Recompute and save conversation rollups inside one `ConversationRollupMutationSerializer.performThrowingSyncMutation` block keyed on the affected conversation IDs.
- Store maintenance is a run of its own, never part of a sync's run. The 6-hour store-wide passes (`DataCleanupService.runStoreMaintenanceIfDue`) are asked for once an incremental run has ended (`SyncEngine.runStoreMaintenanceAfterSync`: after a foreground sync and after a processing task's, never an app refresh's) and take the exclusive `.maintenance` run through `StoreMaintenanceCoordinator`: the shared one for the shared engine, so that they and the daily database tasks run one at a time, and one built on the engine's own `SyncRunCoordinator` for an engine that was given a coordinator of its own (`SyncEngine.init(storeMaintenanceCoordinator:)`). `runIncrementalCleanup`, which is inside the sync's run and ahead of `.syncCompleted`, is the flag-gated migrations only. Never ask for the maintenance from inside a run or a lease: it waits for the boundary its caller holds. It is not asked for after a run whose follow-up is about to run, because the follow-up is the rest of the new mail and would wait behind the passes for the exclusive run: in the foreground the completion answers whether the coordinator queued a continuation (`ForegroundSyncCoordinator.scheduleImmediateFollowUp`) and the engine asks only where it did not, and a processing task's run that needs a follow-up leaves the passes, since its catch-up is scheduled only after the engine returns and never for a task that has expired by then. Do not key the foreground on `needsFollowUp` itself: a cursor held by a message that keeps failing asks for a follow-up after every run, and the maintenance would never be asked for. A maintenance operation runs in a task registered with its run (`SyncRunCoordinator.acquireRunWithTask`), which an account transition's `beginQuiescence()` and the cancellation of the caller (a background task's expiration) both cancel. Cancelling shortens the wait and does not replace it: the operation checks `Task.isCancelled` between its steps and returns, and the run is ended only after it has. A caller cancelled while it still waits for the boundary is answered then, with no task built (`parkUntilIdleOrCancelled`): a fired task is completed only after its handler returns, so a handler parked behind a sync kept an expired task uncompleted for as long as that sync ran. `acquireRun` and `waitUntilIdle` still wait for the run ahead to end. `BackgroundTaskRegistry.runTaskOperation` completes a fired task once, after its cancelled handler has returned, and submits the next request before that. The weekly VACUUM is retired: `DatabaseMaintenanceService.retiredVacuumTaskIdentifier` keeps a handler that does nothing (`retire`) and its `Info.plist` entry, because a device that ran an earlier build can hold a request for it and `BGTaskScheduler` raises on an identifier with no handler. The daily analyze and cleanup handlers await `DatabaseMaintenanceService.persistenceReadiness` (the single-attempt `AppStartupBootstrap.preparePersistenceIfNeeded()`) before anything else, outside the run: a cold background launch reaches them without `initializeApp`, and a handler that touched the stack first made the store's first load, ladder included, ahead of the fresh-install cleanup. Inside the run they decline unless `isStoreLoaded` (read before the lazy container is touched), and no maintenance step runs on a context whose coordinator has no store. The 6-hour passes decline the same way inside their run (`runStoreMaintenanceIfDue(exclusiveRunner:)`), leaving the cadence due. A read whose empty answer lets files or rows be deleted (the two orphan sweeps, `deleteOrphanedAttachments`, `DeletedRowFileReclamation`'s two reads, the account-isolation gate's store inspection) calls `CoreDataStack.requireAttachedStore(in:)` inside its `perform`, outside any injectable fetch: a coordinator with no store answers a fetch with `[]` and no error, so neither `isStoreLoaded` nor the bootstrap's readiness is a witness, and the context's own coordinator is. A new such read does the same. `DatabaseMaintenanceStoreGateTests` (iOS plan only: its runs still reach the shared compose lease registry), `AttachedStoreGuardTests`, `MaintenanceCleanupGateTests`, `StoreMaintenanceCoordinatorTests`, `SyncEngineStoreMaintenanceTests`, `BackgroundTaskRegistryTests` and `SQLiteDatabaseTests` pin this; where `SyncEngine` asks from is pinned from source (`StoreMaintenanceAfterSyncSourceTests`). None of it has been watched on a device: no background task has expired under it and no sign-out has been made during a maintenance run.

## Outbound send (non-idempotent; never resend)

- Gmail `messages.send` has no idempotency key. `sendMessage` uses `allowsRetransmission: false`. Never route a send onto a retrying/idempotent path.
- messages.send rides its own session (`GmailAPIClient.createSendSession`): no connectivity wait, and its own whole-request cap, `NetworkConfig.sendResourceTimeout` (300 s, not the reads' 60 s), because one request carries every attachment and a slow upload that hit 60 s timed out after the barrier into a permanent "Delivery unknown". The 30 s request timeout stays the stall detector (an idle timer: measured against a throttled loopback server, it does not fire while the body is still being written). The cap is per attempt and also sets how long a sign-out's drain and the conversation's next reply can wait for an admitted send (about 420 s with a retry, because the breaker is checked only before an attempt), so raising it is a decision. The retry engine's 120 s breaker must throw a recorded rejection, never `APIError.timeout` for a request that was refused: a 429, and for a send a 401, records `lastError` (the first one recorded is kept) before its `continue`, or a breaker trip after a long upload and a 401 threw `APIError.timeout`, which is ambiguous, for a send Gmail had refused.
- The body is the MIME's own bytes, uploaded to messages.send's upload endpoint (`uploadType=multipart`: a JSON part with the thread ID, then `message/rfc822`) and streamed from a file (`GmailMultipartSendUpload`, `URLSession.upload(for:fromFile:)` in `performRetryingRequest`), never the in-memory `{"raw": base64url}` body, which was about 4/3 of the MIME and let three or four photos on cellular run past the 300 s cap into "Delivery unknown". The file is written before the barrier (a failed write is "Not sent"), every attempt of one send uploads the same file, and it is removed when the send ends; files a killed send left are removed by the next send after `staleFileAge`. The file is the only thing that changed: never let it bring a send onto another session or past the barrier. `GmailAPIClientStreamedSendTests` and `GmailMultipartSendUploadTests` pin it; no send has been made against Gmail's real upload endpoint from this change.
- The transmission-admission barrier is `try Task.checkCancellation()` + `try await beforeTransmission()`, the last safe point before URLSession admits the request. New work goes **before** it, never between it and the request.
- Outcome matrix keys off `TransmissionBarrierState.isPersisted`: pre-barrier failure → the request's `PreTransmissionFailureDisposition`. `.rollBackToComposer` (ComposeView compose/forward, whose composer keeps the content until admission) rolls back the optimistic message + fails admission; `.retainAsNotSent` (chat replies: `sendReply` clears the field at tap and releases the composer at `onOptimisticMessagePersisted`) retains it as definitely-unsent + succeeds admission, writing no `ChatReplyDraft` and requeuing nothing (the composer may already hold the next reply). Pre-barrier cancellation, ambiguous errors and account teardown (`teardownRequested`) always roll back; background-time expiry before the barrier is not a teardown and follows the disposition (`backgroundTimeExpiredWithoutTeardown`), so an offline reply parked in `OutboundConnectivityGate` when the phone locks stays "Not sent". A rollback *merges* a reply into `ChatReplyDraft` (`saveMergingUnsentReply`, never `save`: the slot may hold the next reply); one that cannot write the draft retains the row instead and reports `PreTransmissionRollbackOutcome.retainedAsNotSent`, which must succeed admission, or the composer restores text the bubble still shows. It restores pre-send archive state only if `archiveStateIsOptimisticOnly` (read before the rollup recompute): an archive made during preflight wins. Deterministic refusals (no recipients, threadless reply) belong before optimistic creation, or a Not-sent row would fail the same way on Edit and resend. Post-barrier ambiguous/cancellation → `recordAmbiguousRemoteSend` + succeed (graph retained, no retry); post-barrier definite rejection → retain as definitely-unsent. Misclassifying a new error class is a duplicate-send hazard. Ambiguous = CancellationError, serverError, timeout, decodingError, non-pre-transmission networkError.
- The deterministic RFC Message-ID (`MimeBuilder.messageId(forOptimisticMessageID:)`) is how sync matches the echo. Always pass `messageId:` on outbound calls; dropping it silently breaks convergence.
- Optimistic creation runs inside the cleanup-sensitive gate and, inside that, the turns of the stored conversations it may anchor to, where it reads the store's archive state before it chooses one. The order and the two rules that fail as a hang are in the `MessageActions` note under Conventions. New work in creation goes inside both, and a second route to creation must take both.
- Optimistic conversation hashing must use `AliasManager.shared.getAliases(from: viewContext)` — the context-taking overload, never a cache-only read. It falls back to Core Data when the alias cache is cold (fresh launch, post-invalidate), which is exactly when a self-exclusion miss would hash the optimistic conversation differently from the synced-back echo and fork the chat.
- Inserting an optimistic outgoing message bumps `lastMessageDate` and `snippet` only. Do **not** set `conversation.hasInbox = true` — an outgoing message is not inbox presence, and setting it resurrects archived chats on send.
- On API success, do **not** rename or delete the optimistic row. Sync owns atomic replacement and record consumption (`remoteCommittedSendMutationResolutions` / `consumeRemoteCommittedSendMutation`), inside the same transaction that persists the echo.
- Any conversation merge, dedup, or cleanup pass must exclude conversations named by an in-flight `OutboundSendMutationRecord` (`ConversationMerger` fetches those `conversationId`s and skips them). The optimistic message may still be unsaved on the view context and therefore invisible to a background fetch; deleting its conversation as a merge loser orphans it and dangles the reconciliation record. Same reason `GmailSendService` refuses to anchor an optimistic reply to a deleted or `isRetainedDrainedShell` conversation.
- `missingRecordIsError` is true only for `recordRemoteSendAdmission`; other marker writes must tolerate a record an echo already consumed.
- There is no user-facing resend affordance. Cold recovery (`reconcileAbandonedOptimisticSendMutations`) never retries — it only converts markers.
- "Delivery unknown" is resolved, never retried, by a Message-ID lookup inside an incremental sync run (`DeliveryUnknownProbe`, called from `ReconciliationPhase`; the rules are `DeliveryUnknownProbePolicy`). Found: the run persists the message and its echo consumes the record as any echo does. Reliably not found: the record becomes "Not sent" (`DeliveryUnknownResolution.stageNotSent`, which must keep `retainDefinitelyUnsentOptimisticMessage`'s effects), and Edit and resend is the user's. Anything else is no verdict. "Not found" rests on two witnesses, so keep both: Gmail's `rfc822msgid:` search over every label, sent with `includeSpamTrash=true` (`searchAllMessages`; the API leaves Spam and Trash out by default, and the query's `in:anywhere` is not relied on), came back empty with no next page, and this run's history slice was terminal with no failed fetch (`allowsProbing`), because while a record is ambiguous history admits even the labels it excludes. A run whose missed-message recovery failed to fetch a message it knew was missing gives no "Not sent" verdict (`allowsNotSentVerdict`). Before an empty search is taken as "Not sent", the store is asked too (`DeliveryUnknownResolution.storeAgreesItWasNotSent`), and refuses on a sync ledger row (`AbandonedSyncMessage`) recorded since the send, which may be its echo (a row whose retries ran out is deleted and an unprocessable message leaves none, so then the search is the only witness), on a stored row anywhere carrying the send's own Message-ID (an echo kept without consuming the record), or on a message from the user in the send's conversation, dated within its request lifetime, without one of the app's deterministic Message-IDs, which is what the echo looks like if Gmail did not keep ours. Neither witness sees a sent copy the user deleted forever before the app synced it (history answers 404, which is "gone"), and after a history recovery, whose listing leaves Trash out, only the search covers Trash. Only records stamped with `admittedAt` (set with the in-flight marker, model 7) and admitted at least an hour before the run (`quietPeriod`, on the wall clock) are asked about, never an in-flight one, never in an app refresh, at most three a run, never asked first; every lookup that is not resolved here stamps `deliveryProbedAt` and waits `reprobeInterval` (6 h), so failing lookups cannot hold the run's three for good; a record whose message row is gone is left alone; a record admitted before model 7 may carry another Message-ID in its MIME and stays "Delivery unknown" for good. The writes are staged in the run's context and commit at its save point or die with it; cancellation and account-scoped failures abort the run. Gmail's search semantics for our Message-ID were not measured against a real account.
- Sends flow `reserve()` → `ownPreparation` → `handOff` → `admitTransmission` (the linearization point; after it the send is drain-only). Re-check `isActive(reservation)` after suspensions.
- A reply's `ChatViewModel` can outlive its screen (navigation stays open during a send; the send task retains it). `ChatReplyComposerDirectory` makes the newest presented composer the only writer of the conversation's draft; an off-screen model hands an unsent reply to the open composer or merges it into the stored draft (`returnUnsentReply`), never restores it into itself. A composer that left the screen saves through the cleanup gate, so its save can still be waiting when the chat is opened again (on the Mac, chat A, B, A on arrow keys): the new composer then takes the draft from it in place of the stored one (`handOverOwedReplyDraft`, found through `withdrawnDraftOwner`) and makes the save itself. Only a composer that still owes a save gives its draft (`replyDraftSaveIsOwed`; one that owes nothing can hold less than the store, which may have had an unsent reply merged in), never one that is sending, and only finalized attachments go. Every scheduled draft save must start in `startReplyDraftSave`, or the flag misses it and that draft is lost as before. `ChatView` must keep calling `composerDidAppear`/`composerDidDisappear`. From tap until the reply has a durable owner again the send holds a `ChatReplyComposerDirectory.UnpersistedSend`; while one is held the stored draft is still the reply being sent, so a composer created meanwhile must not restore it (`restoreReplyDraft`), and every exit path must `end()` it (a leak disables draft restore for that chat until relaunch).
- Chat replies to one conversation transmit in tap order: the worker awaits its `OutboundConversationSendSequencer` turn strictly before the barrier, so a queued send is still a preflight registry entry that `closeAdmission` cancels (the wait is cancellation-aware). Any terminal predecessor (succeeded, failed, ambiguous, cancelled) releases the next; nothing is retransmitted. Every path must `finish()` its turn. Only `.reply` requests take a turn (`OutboundMessageRequest.takesConversationSendTurn`): ComposeView compose and forward hold their sheet until admission, so they neither wait on nor hold the turn and are never parked behind a chat reply's upload.
- Before its turn, the worker runs `OutboundConnectivityGate.waitForUsablePath`: on a known-unsatisfied `NWPath` (only `.unsatisfied`; `.requiresConnection`, e.g. idle VPN On Demand, is activated by the request itself — `OutboundNetworkPathMonitor.isUsable`) it waits (cancellation-aware) up to `NetworkConfig.sendConnectivityWaitTimeout` for the path to return, then fails with a pre-transmission `URLError(.notConnectedToInternet)` that the request's disposition decides. It is the only connectivity wait on the send path (the send session never waits for connectivity) and must stay before the barrier. Tests inject `OutboundNetworkPathMonitoring` and a clock; the shared monitor reports satisfied under hosted unit tests.
- Coverage: `GmailSendServiceOptimisticFailureTests`, `ComposeSendOrchestratorTests`, `OutboundMessageCoordinatorTests`.

## Conventions

- **Concurrency:** `actor` for stateful multi-task services, `@MainActor final class ... : ObservableObject` for view models. `SWIFT_STRICT_CONCURRENCY = minimal` is a ratchet floor; `targeted` does not compile today. `@unchecked Sendable` is a debt marker — carry a `///` comment naming the synchronization that justifies it; grep for the current holders.
- **Core Data:** merge policy `NSMergeByPropertyObjectTrumpMergePolicy` is set by the three `CoreDataStack` factories (viewContext, `newBackgroundContext()`, `performBackgroundTask`); a hand-built context must set it itself, as `GmailSendService+OptimisticUpdates.swift` and `ConversationCreationSerializer.swift` do. Save via `context.saveOrLog(operation:category:)` or `await context.performSaveIfNeeded(caller:)`, not `try? save()`. Keep fetches and mutations inside the owning context’s `perform` closure; use the save helpers in `NSManagedObjectContext+Perform.swift` where appropriate. A migration-family load error never deletes the store, in a foreground or a background launch (`CoreDataErrorClassifier.RecoveryAction.migrationFailed`, which used to back it up and delete it on the first failure): Every successful load stamps this build's model ordinal into the store's metadata (`StoreModelCompatibility.modelOrdinalMetadataKey`, written with the next save), and after a migration-family error `StoreModelCompatibility` latches `PersistentStoreLoadError.storeFromNewerVersion` only when that stamp is above this build's ordinal, otherwise `.migrationFailed`; unreadable metadata is `.unavailable`. One rule for all three (Kevin, 2026-11-24): never deleted automatically, Try Again, and the confirmed Reset Mailbox past the usual threshold, as for any load failure; only the words differ, a newer build's store being asked to update and its confirmation saying that updating keeps the mailbox. Never decide "newer" from hashes matching no bundled model: the first model was edited in place while it shipped, so a store an old build wrote matches none, and would be told to install an update that does not exist. Within a process, the launch loop's timed retries and background tasks do not reload a store latched with either of those two (`CoreDataStack.isDeterministicLoadFailure`): each reload re-runs the migration on the main actor; the user's Try Again and a completed reset permit one (`permitReloadAfterDeterministicFailure`). Each new process still makes one attempt, every background wake's included, so a large store whose migration keeps failing runs it again at each wake until the user opens the app (a per-store record of the failure is a follow-up). The stamp is in memory until the next save, so a newer build that saved nothing before it was replaced leaves a store that reads as not newer; that changes the notice's words, not what is offered. The reset removes the store by path, with its `-wal` and `-shm`, so it also clears a store that never attached; a sign-out's `destroyAllData` removes only attached stores. Signing out cannot be reached from the launch-failure screen on either platform. Never mutate the loaded `NSManagedObjectModel` at runtime — schema changes go in versioned `.xcdatamodel` files only. `Services/DatabaseMaintenance/SQLiteDatabase.swift` is a thin SQLite handle used only by `DatabaseMaintenanceService+SQLite.swift` for the daily ANALYZE; it stops its statement when the task running it is cancelled, while it runs or while it waits for another connection's lock (a busy handler of its own, never `sqlite3_busy_timeout`, whose wait nothing can end). Indexing is the 19 `<fetchIndex>` declarations in the current model version — the never-called raw-SQL index/pragma setup that used to sit beside `SQLiteDatabase` was deleted; do not reintroduce hand-written SQL against Core Data's Z-tables.
- **A conversation's messages are asked for by the conversation's objectID** (`conversation == %@`, e.g. `MessagePredicates.visibleInChat(conversationObjectID:)`), never by `conversation.id == %@`: that form joins every message to its conversation to compare a UUID no index covers, and on a store without SQLite statistics it reads the whole message table. A temporary objectID names no stored row, so an unsaved conversation keeps the UUID form (`VirtualScrollState.transcriptPredicate`). `MessagePredicates.unreadInInbox` is spelled `isUnread != NO` on purpose: with `== YES` SQLite drives the fetch from the mailbox-wide `byIsUnreadIndex`. `ScaleQueryPlanTests` (`--performance`) pins both plans and the three fetches of `applyInboxRollup`; a new hot fetch over `Message` gets a plan test there. A chat's scroll state keeps the conversation's objectID its first page load resolved (`VirtualScrollMessagePage.conversationObjectID`) and hands it to every later load, so only the first looks the conversation up by its UUID. It is never looked up on the view context for a page load: that lookup is a fetch on the main thread.
- **`MessageActions` changes labels and read state only on a background context** inside the conversation's `ConversationRollupMutationSerializer` block, never on the view context: a label change there loads every member of that label into it. The view context learns of the change from the save's merge, so nothing may read the result from a view-context object in the same turn, and a test (whose stack does not merge by itself) calls `refreshAllObjects()` first. The rollup after a one-message change is `applyInboxRollup`: counts and a one-row fetch against the store, with the changed message left out by ID and added back from memory. Do not go back to fetching the conversation's INBOX messages to count them. Archive and Report Spam on a conversation take their conversations' turns and never the cleanup-sensitive gate: the gate is every send's, draft save's and cleanup pass's, and an action that held it kept all of them waiting for as long as it ran, and itself waited for a whole full cleanup. What keeps a send from being archived with its conversation is on the send's side (`GmailSendService.createOptimisticMessage`). Inside the gate the send takes the turns of the stored conversations it may anchor to (`ConversationRollupMutationSerializer.performThrowingAnchoredSendMutation`), so it runs wholly before an Archive of one of them or wholly after it, and inside those turns it reads the store's archive state for them (`adoptStoredArchiveState`), because the view context has another context's save only once it has merged it. A send that chose its conversation while an archive was still saving, or from the view context's copy of one that another context had just archived, anchored to it without reactivating it and was archived with it. Both halves are needed, and the read is at the send, not at the writers, so that it holds for the launch repair and the cleanup passes too. The order is the gate, then the turn, and two rules fail silently as a hang: a holder of a conversation's turn must never ask for the gate, and nothing may ask for the gate and a conversation's turn in one call. The cost is that a send waits for whatever holds its conversation's turn (an Archive of that chat, a mark-read batch, a sync save that touches it) and holds the gate while it waits. A conversation the store already has the action applied to is left alone (`isAlreadyApplied`), because its list row stays until the save reaches the view context and can be swiped again. A label that could not be read is not a label the store lacks (`fetchLabel` throws), and the action then saves and queues nothing. The chat-open unread snapshot is started in the turn the chat opens (`startUnreadInboxSnapshot`, a detached task) and only its result is awaited in the chat's own task: awaited whole through `MessageActions`, which is main-actor, it waited for the main actor, and a message saved meanwhile was marked read with the rest. Keep it `Task.detached`: a plain `Task` there inherits the main actor and waits for it in the same way.
- **Managed objects never cross context or actor boundaries.** Pass `NSManagedObjectID`, re-resolve on the destination context, map to `Equatable` value snapshots (`ChatMessageRowModel`) for SwiftUI.
- Message bodies and attachments live on disk, not in Core Data. Route body-file access through `HTMLContentHandler` (process-wide account boundary), never raw `FileManager`. Never read `Attachment.localURL` / `previewURL` directly for rendering or opening — use `readableLocalURLValue` / `readablePreviewURLValue`; legacy ID-only remote paths and `local_inline_*` files stay persisted only long enough to trigger migration and must never reach a reader, because an attachment-scoped path can be shared by sibling messages. Recovery paths recompute the deterministic ID from *this* message's MIME part (`AttachmentPaths.synthesizedInlinePayloads`) to prove the bytes belong to the row.
- **Mail the app can download again is left out of device backups** (`BackupExclusion`, scalability review step 7): the `Messages`, `Previews`, `Avatars` and store `Backups` directories whole, and in `Attachments` each downloaded file, because that directory also holds the `local_` originals of attachments the user added, which cannot be downloaded again and are never marked (`AttachmentPaths.isRedownloadable`, read from the file's name). The mark only advises the backup; a marked file is never purgeable. It is written in one function, which on the Mac writes nothing outside the App Sandbox (`BackupExclusion.marksFiles`, the tripwire's question): unsandboxed, the directories are the user's own `~/Documents/Messages` and `~/Documents/Avatars`, and a mark would drop them from Time Machine. Never write `isExcludedFromBackup` anywhere else. Four things fail silently, the first three measured on macOS 27.2 and the iOS 27.0 simulator and pinned by `BackupExclusionTests`. The mark is the directory's or the file's own, so a directory made again has none: every place that creates one of the four marks it, and marks it whether it made the directory or found it, which is what reaches an installation from an earlier build; a new place that creates one must do the same. An atomic write makes a new file, so a download is marked after each write (`AttachmentPaths.saveData`), and a write to `Attachments` that does not go through `saveData` calls `AttachmentPaths.applyBackupPolicy(toFileAt:)`. `FileManager.copyItem` copies the mark, so any copy of a stored attachment that leaves the store has it taken off: a copy handed to the user (`AttachmentFileExport.copyOut`, which every save and drag goes through; left marked, the user's saved file is missing from the user's own backups) and a copy that becomes an original (the forward's, `ComposeAttachmentManager.copyAttachmentForForward`). Quick Look is handed the stored file itself and its share button hands that file on, so the files a Quick Look is given have the mark taken off before it is shown and given back by name when it closes (`QuickLookBackupMark`, from `QuickLookPreviewController` on iOS and `AttachmentQuickLookModifier` on the Mac); a new way of showing a stored attachment to something that can share it does the same. And the store is still backed up, so a restore brings back rows without their bodies and attachments, which are then fetched again: nothing may treat a missing body file as a body the message never had. Not measured: no backup or restore has been made, and whether a destination of the share sheet copies the mark is unknown, which matters now only for a file an app ended with Quick Look open left unmarked until the next daily orphan sweep.
- **Conversation keying** is `Conversation.participantHash` from `calculateParticipantHash` (`p|`) or `calculateListConversationHash` (`l|`). Both are marked CANONICAL — never duplicate the hashing. A list (`l|`) title must **never** be derived from a message's sender at creation (senders vary post to post): use the List-Id display phrase — sanitized by `ParsedListId.sanitizedDisplayTitle`, which rejects provider machine tokens (Mailchimp's `<token>mc list`, Brevo bare tokens, base64-of-numeric-id tokens on any domain) — falling back to the normalized List-Id. The one sanctioned sender-derived exception is the rollup upgrade: a stored identifier-derived title upgrades to the single distinct sender's From name (`ConversationRollupUpdater.updateDisplayNameOnly`). Stored list titles are re-evaluated every launch (`ConversationLaunchRepairCoordinator.repairListConversationTitles`), so a `ParsedListId` heuristic improvement ships **without** a `hasRefreshedConversationNames` key bump — the per-launch pass heals stale titles; bumping the key re-derives every conversation's name on every device. Existing-message *repair* must not apply new-arrival epoch semantics — reuse a durable List-Id conversation whether active or archived and leave `archivedAt` untouched (`MessageConversationRouter.existingConversationObjectID`). `Message.strictParticipantSetIdentity(myAliases:)` returns nil when a message has no `MessageParticipant` rows, and nil means **do not re-home**: `senderEmail` alone cannot reconstruct To/Cc. Current optimistic sends persist known From/To rows, but legacy or partially imported row-less messages remain in place rather than being guessed into a note-to-self chat.
- **A display name is the sender's, and so is any address written in it.** An address header is read one mailbox at a time: `EmailAddressListParser.addressTokens` splits at commas outside quoted strings, comments and angle-addrs, and `EmailNormalizer.mailboxAddress(inToken:)` reads the mailbox's address as the last `<…@…>` outside quoted strings and comments (`extractEmail`/`extractDisplayName` take the first mailbox; `EmailAddressListParser.mailboxes(from:)` every one). Taking the first `<…@…>` anywhere read `"Boss <boss@corp.example>" <x@attacker.example>` as Boss, keyed it into Boss's chat, and with the user's own address in the quotes made it `isFromMe` (architecture review 2026-11, gap-mime-decoding-i18n#2). `web/src/identity/normalizeEmail.ts` ports both rule for rule, and the golden corpus pins them on both platforms. Three things fail silently. Never join a parsed name back to its address (`"\(name) <\(email)>"`) and parse the result: the name is already decoded and unquoted, so its commas, brackets and parentheses are read as structure, and the router and the persister did exactly that (a phantom participant from `"bob@old.example, Bob"`, an encoded name that took the recipient's address); pass the two values (`makeConversationIdentity(participants:…)`, `MessageParticipantFactory.create(email:displayName:…)`). `isEmailAddressShapedDisplayName` keeps the old anywhere reading (`firstAddressAnywhere`), because it asks whether a *name* embeds an address, which is how `Boss <boss@corp.example>` as a name is hidden; never point it at the header reading. And messages stored before the fix keep their sender, rows and chat: no raw From is kept, and nothing re-keys them.
- **One chat per contact:** a participant is a person, not an address. Addresses that one contact card lists are linked (`ContactLinkedAddresses`), and `makeParticipantSetIdentity` hashes linked addresses as one participant, so someone who writes from two of their addresses is one chat. With nothing linked the hash is the plain address-set hash, which is what the web app computes and the golden corpus pins. Six things fail silently. Every hash is made with the map `ContactLinkedAddressStore` has adopted (`snapshot()`, the default of every `contactLinks:` parameter); a pass that hashes many rows reads it once and passes it, as it does the aliases, and a hash made with any other map forks the chat. A new map is adopted in one place, `DataCleanupService.unifyConversationsByContactIfNeeded`, the first step of a sync run's cleanup: the run still owns the store and the cleanup-sensitive gate is held, so nothing routes or sends between the adoption and `fixAndMergeIncorrectParticipantHashes(scope: .conversationsNaming(…))` giving the stored conversations the new hashes (archived ones take the hash and are never merged). A conversation a pending send or a saved reply draft anchors takes the new hash there too, in place, with its rows, type and messages left for the anchor's release (`ParticipantHashRepairScope.givesAnchoredConversationsTheirHash`): left on its old hash it loses that person's mail to a second chat for as long as the draft is kept. Only a conversation a chat-preview retry anchors keeps its hash, and maintenance still leaves every anchor untouched. Never call `refreshIfNeeded()` from anywhere else. Contacts that cannot be read are never an empty map: while access is undecided or after a failed read the adopted map stays, or one bad launch unlinks every chat. Access the user has denied, or the device restricts, is an answer and not a failed read: `refreshIfNeeded()` asks the authorization at every call (turning access off reports no change in Contacts) and then drops the map and its copy in defaults (`ContactsAccess.withdrawn`), which unlinks as an edited card does. A link is only what one card states: an address on two people's cards links nothing, a card contained in another is that card again, and nothing is chained through a third address; loosening any of these merges two people's chats. A conversation's rows hold one address for each person, the one the message that opened it carried, never one the card merely lists, because a reply reads the rows; a reply to a linked participant goes through `ReplyLinkedAddressPolicy`, which exchanges the row's address only for one the message being replied to carried. And unlinking moves no messages: mail from the address opens a chat of its own again, and what was merged stays merged. So a merged chat can hold mail of someone its rows no longer name, and a reply there is not addressed from the rows: where the message being replied to is fully known and the rows would reach someone who was not on it, or miss the person who wrote it, the reply goes to the people on the message (`ReplyLinkedAddressPolicy.rowsCanAnswer`, asked by `ReplyMetadataBuilder.recipientsOverrulingRows`). Rows that only leave someone out still answer, as they always have, and a conversation with no usable row still fails closed. The chat's title is made from the rows, so such a reply goes to people the title does not name: the composer names them in the row above its field (`ChatComposerState.announcedReplyRecipients`, `ReplyIndicatorPolicy`), and the send logs it. So does a reply that follows a Reply-To header to an address the rows do not hold: what is announced is read from the outcome (`ReplyAddressing.differsFromConversationPeople`: the recipients are not the rows' people), never set by the rule that addressed the reply, so a rule added later cannot address a reply elsewhere unseen. The composer never works out the recipients for itself. It asks the send's own decision (`OutboundReplyContextBuilder.replyAddressing`, which is `ReplyMetadataBuilder.replyAddressing` over the stored rows), after a screen that settles the ordinary chat in the turn its target changes, with no alias load (`ReplyMetadataBuilder.rowsCertainlyAnswer`). That screen may say "ask" where the reply does go to the rows' people and must never say "settled" where it does not, or a redirected reply names nobody (`testRowsCertainlyAnswer_isNeverTrueWhereTheSendOverrulesTheRows`). The answer is asked again whenever the reply target changes, whenever a sync completes (`.syncCompleted`) and whenever a cleanup run of `DataCleanupService` ends (`.conversationCleanupFinished`), because links, rows and aliases change with no change of target, and a chat on the Mac stays open across them. Both posts are needed: the cleanup runs are the only writers of links and rows, and the daily database cleanup runs outside any sync, while stored aliases are saved by a sync alone. A new orchestration in `DataCleanupService` must call `announceCleanupFinished` when it ends, and the chat's subscription keeps its quiet interval, which makes one refresh of the two posts an incremental sync makes. The recipients are drawn through `ReplyIndicatorPolicy.announcedRecipientsText`: an address longer than 28 characters is cut before its `@` and never after it (the start of a long domain can read as somebody else's), and beside a quote the row names two and counts the rest, because a machine's Reply-To address at full length took the whole row and the subject with it. Three things keep that shortening from hiding who gets the reply. The recipients are named with those the title does not name first (`ReplyAddressing.recipientsToAnnounce`, from `ReplyLinkedAddressPolicy.recipientsOutsideConversation`), never in the reply's own order, which is partly the sender's: a Reply-To header that put the chat's own people first had the row name them and count the stranger. The cut keeps both ends of the part before the `@`, which at a mailbox provider is who gets the mail: cut to their start, an address and one made by adding to its end were drawn the same. And the header carries the label whole (`unabridgedLabel`, read through `ReplyIndicatorPolicy.wholeLabel`): for the `To:` row wherever its short label says less, and for the quote row whenever it announces anyone, because that row's one line can end before even an uncut label does. The bar's own `To:` row, which wraps, draws it, a one-line row gives it to VoiceOver, the Mac's capsule shows it as its tooltip, and the iPhone's quote row opens on a tap to draw it, wrapped (`ReplyIndicatorPolicy.quoteRow`; a chevron is the only sign that it opens, and `ChatReplyBar` closes it when the header changes). The iPhone's rows are `ChatReplyBarHeaderRow`, and three things about a row of text there fail silently. Its text is no taller than `ReplyIndicatorPolicy.wrappingLabelMaxHeight` and scrolls past that: how many addresses a Reply-To header names and how long each is are the sender's to choose, and the composer's height is the transcript's bottom inset, so a row as tall as its text let one message take the screen. The limit is a `frame(maxHeight:)` and a `fixedSize` together: without the `fixedSize` every row, one naming one person included, is as tall as the limit. And text that wraps is drawn through `ReplyIndicatorPolicy.wrappingLabel`, which marks each address as text in no language: unmarked, a line break hyphenates an address (`accounts.sub-`, then `sidiary.example.com`), which is how another domain is written. The mark is for line breaking alone, and the text's accessibility label is the plain string. `ChatReplyBarHeaderRowTests` mounts the row and measures it; that a tap opens it, and what VoiceOver and the tooltip are given, are pinned from source (`ReplyIndicatorWholeLabelSourceTests`). The iPhone's rows were drawn off screen in the test host (iOS 27.0). No row has been seen in the app, and none has been tapped or scrolled. The map is the device's Contacts, not account data, so it outlives a sign-out and is no participant of the account boundary; the user's own addresses are left out when a hash is made (`canonicalAddress(for:excluding:)`). The shared store holds nothing under unit tests: a test passes `contactLinks:` or builds a store with its own `loadContactAddressLists` and `contactsAuthorizationStatus` (`AddressBookStub` is both). `ContactUnificationCleanupTests`, `ContactLinkedAddressesTests`, `ContactLinkedAddressStoreTests` and `ReplyLinkedAddressPolicyTests` pin this. The Core Data ones were written without a Mac; they have since run in CI and on the iOS 27.0 simulator. Nothing has been seen in the app: the merge has not been watched on a device, Contacts and their authorization have only ever been a stub, and what the authorization reads as on a launch before the first unlock has not been measured.
- **Self-aliases from Contacts** (`ContactsSelfAliasProvider`, read by `AliasManager`) add to the user's own addresses the addresses of a card that lists one of them, and that set decides `isFromMe`, is removed before every participant hash (it keys note-to-self) and is filtered out of reply recipients. So a card counts only when none of its other addresses is on a card that lists none of the user's addresses (`SelfContactCards`): a household card for a shared Gmail account, or a company card listing colleagues beside the send-as address, made the other person's mail the user's own bubbles and their chat note-to-self (architecture review 2026-11, contacts-person#1). The Mac's "me" card counts whatever it lists, and its addresses are trusted when other cards are judged (they never disqualify a card, but only an account or send-as address makes a card count). Deciding needs every card, so the provider walks the address book (email keys only) whenever a matched card lists an address beyond the known ones or a Gmail address matched no card by predicate; a walk that fails, and limited Contacts access (which walks only the shared cards), admit no such card. The rule reads addresses, not names: a card that lists the user beside someone with no card of their own still counts, and any card naming no account address that lists one of the user's other addresses (a leftover self card, a team card, a partner's card with the user's iCloud address) drops the user's own card. Still open from that finding: the set is read live, not adopted and persisted like the link map, so an edit to any card (the partner's too) can move an address in or out of it; stored `isFromMe` and chats merged under the old rule are not repaired; the 6-hour maintenance re-hash moves stored active chats to the new hashes. `SelfContactCardsTests` and `ContactsSelfAliasProviderTests` pin this; Contacts have only ever been a stub.
- **Participant display order:** a conversation's participants are shown in ascending order of normalized email address (`ConversationParticipantExtractor.participantsInDisplayOrder`): the loaded title, the avatar stack, the Participants sheet and the stored `Conversation.displayName` all walk it, and the address-joined fallback title sorts by the same key (`PersonDisplayNameResolver.fallbackConversationName`). Never show `conversation.participants` in the order the set iterates, which changes from one load to the next (`ConversationParticipantDisplayOrderTests`). This is display only and has no part in `participantHash`. The stored title leaves out the user's own addresses as the loaded one does, read from the stored `Account` row (`ConversationRollupUpdater.storedSelfAddresses`: no Contacts self-aliases, because the stored title reads nothing from Contacts), except where they are the conversation's only other participants.
- **HTML nesting depth is the sender's:** every SwiftSoup parse of a string goes through `EmailDOMParseAdmission` (`parseDocument`, `parseBodyFragment`, `parseFragment`), never `SwiftSoup.parse` or `Parser` directly (`EmailDOMParseAdmissionSourceTests` scans the app for it); `Element`'s HTML-taking methods (`html(_:)`, `append(_:)`, `before(_:)` and the like) parse too and take only strings the app builds. SwiftSoup releases a tree, and the `EmailDOM` walkers read one, by recursion, and about 1,030 levels overflowed a 512 KB thread in Debug (1,270 in Release; every sync task runs on one), which was a crash loop at sync. So no tree deeper than `maximumDepth` (512) reaches a caller, and none is built or released on the caller's stack: a byte scan bounds the depth, a bound within 512 parses here, one past `maximumBoundForMeasuredParse` is refused unparsed, and one between is parsed and measured on a thread of its own with a large stack. Cost is bounded as well (`ParseCost`), for the super-linear steps of SwiftSoup's parse that are known: depth × tokens (every `<`, since `<?>` splits text with no tag and every run of text searches the open elements), the rebuilding of formatting elements the builder closed but keeps (a search of the open elements for each and its attribute count squared, at every token), a `title`'s end-tag search at every tag in it, and the active-formatting comparisons, and the adoption agency's move of its furthest block's children (n children cost n², so the scan counts the nodes each held element may have been given and charges the widest block that may be moved); a body past one of their limits is refused unparsed (`tooCostlyToParse`). The child count rests on the scan knowing which elements the builder certainly held (`isRobustlyOpen`): where the scan closes an element the builder may already have closed, the builder may close a lower one instead, and anything counted on such an element passes to the one below it when it is popped. The scan follows SwiftSoup's rules where they differ from HTML's (its `dialog`, `main` and `xmp` close no `p`; its head takes a `command`, so a `noscript` after one is the head's, read as text; a cell or an `object` can leave its marker in the active formatting list, where a later clear stops), and the off-suite comparison that found those patched SwiftSoup to record what the agency moved. A new SwiftSoup, or a newly found super-linear step, needs a term there. A refusal throws `EmailDOMParseRefusal`, which runs each caller's existing failure branch; it must never become a throw out of `processGmailMessage`, and the sanitizer answers it with escaped text, never its legacy regex pass, which a split tag (`<me<meta>ta …>`) gets through. The scan must never under-count (the measuring backstop only covers release, after the tree was built on the caller's stack): it tokenizes as SwiftSoup 2.13.5 does, quirks included, and `EmailDOMParseAdmissionTests` compares it with SwiftSoup over generated tag soup, which a SwiftSoup upgrade must pass again. Bubble derivation reads at most `ChatBubbleTextProcessor.extractedTextUTF16Limit` of extracted text (`cappedExtractedText`); never cap the HTML, `bodyText` or `cleanedSnippet`.
- **Text derivation reads the sender's text whole, so no step of it may be super-linear in that text.** The cap above bounds only the bubble's text: `bodyText`, `cleanedSnippet` and every step ahead of the cap read the whole body, and a regex tried at every start of a run it then reads to the end of is quadratic. Measured on the iOS 27.0 simulator before the fixes: 40 KB of unclosed `<!--` held a message's ingest for 15 s, 8,000 blank lines for 50 s, one line of 16,000 `x` or digits for 14 to 35 s. Four things hold it. The markup steps of `TextProcessing.extractPlainText` and the snippet's preparation go through `HTMLMarkupScan` (`containsLikelyHTMLMarkup`, `HTMLBlockRule`, `replacingBreakPairs`, `replacingTagsEndingAtTagEnd`, `removingHiddenElements` and `HiddenElementRule`, which `HTMLMeaningfulContentChecker` uses too, and `replacingTagsEndingAtTagEnd` again for `RichContentClassifier`'s two tag regexes, and `collapsingLineBreakRuns` for the whitespace collapse's `(\s*\n\s*){2,}`, which was cubic on no-break spaces), each the result of the walk or regex it replaced, read once, except that the hidden-element scan meets a name's close tag ignoring ASCII case only (the regex's backreference folded case fully, `</ß>` closing `<ss>`, and handing such names back to it made the whole message quadratic again); `HTMLMarkupScanTests` compares them over generated markup, so a change to one of those rules changes both or neither. A pattern that starts with a newline and then `\s*` crosses runs of blank lines: `EmailDOMQuoteRemover`'s text markers go through `LineStartMarkerSearch`, which tries each run once. `EmailPatterns.address` starts only at the start of a run of its local part's characters (`(?:(?<![A-Z0-9._%+-])|\G)`), which changes no match (`EmailPatternsTests`); any new pattern whose first atom is a repeated class needs the same guard or its own proof. Apple Mail's quoted attributions in `PlainTextQuoteRemover` are tried at no more than `quotedAttributionStartLimit` starts. A deterministic stall is not a per-message failure: `processGmailMessage` never throws for cost, it is bounded instead, and it checks cancellation between its derivation steps, so an expired run records no verdict rather than finishing the message. Still super-linear and open: `ChatBubbleTextProcessor.htmlTagPattern` on a plain-text body (`<a\n` repeated: 6.4 s at 60 KB, from `RichContentVerdictResolver` in the persist phase), and `RichContentClassifier.stripAppleRichLinkPreviews`, whose close-tag search is linear but which mutates the string at each removed block (12,000 blocks, 816 KB: 6.5 s, -O). Gaps measured and left (the parse gate's, not this code's): a start tag with thousands of duplicate attributes (`<a<a<a…`), and a body between the gate's two depth bounds, parsed and refused again at every stage of the cleanup chain.
- **The body-reading launch passes quarantine a row that kills the app** (`LaunchPassRowQuarantine`): each marks the row it derives in `storage.migrationFlags` and clears the mark when the derivation returns, a mark another launch left is that row's death, and three deaths quarantine it. A quarantined row keeps its preview and its unknown verdict, and the cursor moves past it. The keys embed the pass's migration key, so a bump of the derivation version or verdict epoch gives every row another chance, and none of them is a `chatPreviewRepairCheckpointKeys` key, which conversation maintenance reads. A new pass that derives stored bodies takes a guard of its own. Sync ingest and bubble loads derive the same bodies unguarded.
- **Untrusted URLs from email content:** any fetch of a URL that came out of message HTML (remote images, link previews, Drive metadata) goes through `SSRFGuardingURLSession.shared`, never `URLSession.shared`. That session blocks redirects to private/loopback/link-local/reserved addresses, but it only sees *redirect* targets, so the caller must also reject the initial URL with `PrivateNetworkAddressDetector.isPrivateOrReserved(_:)` (`HTMLRemoteImageAttachmentFallback.isEligibleCandidate` is the reference call site). Both halves are required: public-looking host → 302 → internal IP is the attack the pair exists to close.
- **Every `WKNavigationDelegate` the app sets implements `webViewWebContentProcessDidTerminate`** (the reader's coordinator, `BaseEmailWebView`'s, the pool's `WarmNavigationDelegate` and the snapshot render session). Without it WebKit reloads a dead view by itself, and for a load still in progress it fetched the load's base URL, the sender's `https://<From domain>/`, from the network as an `.other` navigation the reader's policy allows (measured on the iOS 27.0 simulator with a SIGKILL of the WebContent process, 2026-11-24; a process killed after its load finished was left blank). A view reloads only the content it already holds, never a URL, at most three times for one content and signature (`EmailWebViewLoadCoordination.admitsReloadAfterWebContentTermination`). `updateWebView` reloads whenever `needsReload` holds, so without the bound a page that crashes WebKit reloads for as long as it is on screen. The bound is a count and nothing else: a re-arm on the reload having painted was tried and left a view dead whose reload, made during a background launch, was killed before it could paint. A failure carrying `WKError.webContentProcessTerminated` is ignored, because handled as an ordinary failure it resets the signature behind the latch. A pooled view is dropped when it dies (`handleWarmWebContentTermination`, or `discard` from the reader that holds it checked out, matched by the view's identity, with no teardown of the reader's view) and never warmed again by the handler, because a warm is account work only a generation-capturing caller may start. A delegate added later does the same.
- **Logging:** only `Log.debug/info/warning/error(_:category:)` and `Log.diagnostic(_:level:_:category:)` (e.g. `Log.diagnostic(.startup, level: .info, "…", category: .general)`), always with an explicit `category:`. Redaction is a hard rule at the call site (OSLog cannot redact — the pipeline emits `%{public}@`): `Log.redact(email:/address:/url:/error:)`, `Log.hashIdentifier(_:)` for message/thread IDs. Pass errors to `error:`, not string interpolation. `ScopedLogger` (via `LogCategory.sync.logger`) is live and is house style inside `Services/Sync`; prefer it there, `Log.*` elsewhere.
- **Background-run journal (iOS):** `BackgroundRunJournal` keeps the last 20 background-task runs (task, start, end, `BackgroundRunOutcome`, expired, reported) in the preferences, for Share Diagnostics. A `started` entry is written when a task fires and replaced at completion, so a run the process did not live to complete (watchdog, jetsam) still shows. A run with no usable session is `signedOut` (durably signed out) or `noSessionYet` (held after a failed restore, or needing a new sign-in); both report success as before. It is written in `BackgroundTaskCompletionLatch.complete(success:beforeReporting:)`, before `onComplete`, because iOS may suspend the process as soon as `setTaskCompleted` returns; the expiry recorded comes from the same lifecycle transition as the result reported, so they cannot disagree. Both runners write it (`BackgroundSyncManager.runBackgroundTaskOperation`, through `performAuthoritativeSyncOutcome`, whose `reportsSuccess` is exactly the old Bool, and `BackgroundTaskRegistry.runTaskOperation`). Nothing in the hook may wait. An expired or abnormal run logs one warning line. It holds no mailbox data: not account data, left in the preferences by a sign-out on purpose. Hosted unit tests get a throwaway defaults suite from `.shared`.
- **MetricKit records (iOS):** `MetricKitDiagnosticsRecorder`, started in `App.init` inside the `!isRunningUnitTests` block and `#if os(iOS)` (`MetricKitRegistrationSourceTests`), keeps each diagnostic and daily metric payload in `Caches/Diagnostics` through `DiagnosticsRecordStore` (40 files, 4 MB, the earliest written pruned first: names start with a sequence number, never a time, so a clock set back cannot reorder them; only its own `mx-` files are ever removed; file work on a utility queue, never awaited; a failed write is logged once and dropped). What is kept is `DiagnosticsPayloadProjection`'s allowlist and nothing else: an exception's `composedMessage`, `arguments` and `formatString` never are (they can hold an address or a subject), call-stack frames keep binary, offset, address and sample count only, `virtualMemoryRegionInfo` is left out (free text that can name a mapped file), metric payloads drop `signpostMetrics`. A key MetricKit adds later is dropped until it is added to the allowlist on purpose, except inside a metric section already listed (`metricSectionKeys`), which is kept whole because each is numbers and units: check a section for free text before listing it. The iOS list's filter menu offers Share Diagnostics…, which builds `DiagnosticsReport` (versions, OS, records, the background-run journal; no account, no mail, no logs) only when the user shares it. Nothing is sent off the device. The records hold no mail, so they are not account data and a sign-out leaves them.
- **DI:** default-valued initializer parameters — `.shared` defaults for services, `@escaping @Sendable` closures for behavior/time (`SyncClock`, `makeBackgroundContext`, `saveContext`). New code takes a narrowed feature bundle from `Dependencies` (`makeChatDependencies()` etc.) rather than reaching for `.shared`. Top-level views get `Dependencies` and `AuthSession` via `@EnvironmentObject` (see `Dependencies.swift`'s own usage doc); child views and services take constructor injection with a `Dependencies.shared` fallback.
- Errors are domain `enum X: LocalizedError` with an `errorDescription` switch and doc comments distinguishing near-identical cases. No release-path `fatalError`.
- Comments here are load-bearing "why" notes recording past bugs and deliberate non-obvious choices. Preserve them; an unexplained deviation reads as a defect. One type per file, large types split as `Type+Facet.swift` with the base file's header enumerating the split. `///` doc comments only.
- View decisions live in pure `enum XPolicy` static-function namespaces so bodies stay declarative and testable.

## Testing

- 100% XCTest — `import Testing` appears nowhere. Names are `test<Subject>_<scenario>_<expectedOutcome>`.
- Use `TestCoreDataStack`; never construct `NSPersistentContainer(name:)` in a test (a second live model breaks `+[NSManagedObject entity]` and crashes fixture builders under parallel testing). It intentionally uses one process-wide model, a lock around container creation, a private-queue "viewContext", and a never-deallocated graveyard. Save via `stack.saveViewContext()`, never a bare off-queue `context.save()`. `.sqlite` mode exists for persistent-history tests; automerge is opt-in because it races test bodies.
- A `@MainActor` suite whose code under test touches its context directly (fetch/save/delete with no `perform`) takes `stack.makeMainQueueViewContext()`, never `stack.viewContext` — it is private-queue, so every such access is off-queue, which trapped under `-com.apple.CoreData.ConcurrencyDebug 1` and crashed CI's test runner. Route that suite's fixtures, saves, resets, and assertions through the returned context too (a suite-local `saveViewContext()` and `viewContext.reset()`); `stack.saveViewContext()` / `resetViewContext()` act on a different context. `MainQueueMessageActionsCoreDataStack` is the `MessageActionsCoreDataStacking` wrapper for suites that construct `MessageActions`. Prove any new conversion with the ConcurrencyDebug flag before and after.
- A Mac-plan suite that asks AppKit about a mounted SwiftUI view (a hit test, a right-click's menu, an event handed to a view) mounts it with `MacOffscreenHost` in a window from `makeTestHostWindow()`, and one that needs a message's row around an attachment uses `MacMessageRowStandIn`, which hands its menu entries down as `ChatMessagesView` does; `FileBackedAttachmentFixture` makes an attachment with a file in the test's own directory. Do not write another copy of any of the three in a test file. A suite that needs a window with a sheet attached uses `SheetStubWindow`, and no stand-in window may outlive its test: a window that is never shown is still one of `NSApp.windows` while it lives, so one that leaked was a second mailbox window, with a sheet attached, for every suite after it.
- Where the code under test can hand back its task, await the task (`RetiredAccountDirectoryTests` awaits `sweepLeftovers`'s); CI's per-test execution allowance bounds the await. Otherwise bound waits by wall-clock deadline with a poll interval — copy the nearest per-suite private `waitUntil(timeout:pollIntervalNanoseconds:condition:)`; there is no shared version in `TestSupport/`. Never wait by a fixed number of `Task.yield()`. Use `FakeSyncClock` for backoff/pacing, not real sleeps.
- A suite that pins something from source text reads the file with `repositorySource(_:)` (`TestSupport/XCTestCase+RepositorySource.swift`), by its path from the repository's root. Do not write another reader that walks up from the test file's own `#filePath`: the older source suites still have one each, and each breaks without a word when its file moves to a directory of another depth.
- Test retry/backoff semantics against the **real** `GmailAPIClient` through `StubURLProtocol` — mock-based retry tests are vacuous. `MockGmailAPIClient` is for everything else.
- Avoid the real Contacts store in tests: inject `contactEmailLoader` / `accessRequester`, and `loadContactAddressLists` and `contactsAuthorizationStatus` for a `ContactLinkedAddressStore`.
- Anti-masking is house style: tests guarding a fix carry a `Revert-check:` comment naming the production symbol whose removal makes them fail, and a `HONEST SCOPE` comment where a test cannot survive a revert. Revert-check every new regression test hunk-by-hunk.
- Message cleaning / preview routing / newsletter scoring regressions go into `esc-chatmailTests/TestSupport/Fixtures/golden_message_corpus.json`, replayed by `GoldenCorpusReplayTests` in `esc-chatmailTests/Sync/MessageProcessorTests.swift`.
- Isolate tests touching process-global singletons with UUID-suffixed identifiers plus explicit invalidation; there is no automatic global reset.
- Unit tests run hosted in the app process, and `initializeApp()` deliberately no-ops under `RuntimeEnvironment.isRunningUnitTests`. Prefer `CoreDataStack(persistentContainerForTesting:)` over `.shared`.
- There is no UI test target (the never-run `esc-chatmailUITests` and the app's `UI_TEST_MODE` / `UI_TEST_AUTHENTICATED` launch-argument hooks were removed). `PerformanceRegressionTests` runs only under `--performance`.
- The scale harness (`docs/scalability-review.md`, step 4) also runs only under `--performance`: `ScaleQueryPlanTests` and `ScaleHubFaultTests`, on a SQLite store of 120k messages. A change that alters a fetch's SQL, an index, or what a sync write touches is checked there, and it asserts structure, never a time. `ScaleStoreTemplate.s2.makeStack()` seeds the store once for the process (about half a minute) and gives each test its own copy; `.analyzed` gives a copy SQLite's statistics, and a plan is asked about in both states, because a store has none until its daily background ANALYZE has run. `SQLiteQueryPlanRecorder.record` returns the plans SQLite made for whatever Core Data ran inside the closure, so call the production code that builds the fetch and never a copy of its predicate. Four things fail silently. No plans is not "no scans": unwrap the plan a test is about, and check what the fetch returned, before asserting on it. An assertion the app does not meet yet is wrapped in `XCTExpectFailure`, one wrapper for each assertion, naming the review item: it is strict, so the fix that makes the assertion pass fails the test until the wrapper comes off, in that fix's own change. A context holds what it has registered weakly, so after a save a row nothing else holds is gone, with whatever its relationships had read: `ScaleHubFaultTests` measures on a context that keeps its rows (`makeContextUnderTest`, which sets `retainsRegisteredObjects`), and on an ordinary context a label removal and a deletion that each read a hub measured as reading nothing, and a write that read 20,000 messages through another relationship counted none of them. And the recorder turns on Core Data's SQL debugging through `+[NSSQLCore setDebugDefault:]` and reads the plan's rows off standard error, neither of which is public API: `SQLiteQueryPlanRecorderTests` and `ScaleStoreSeederTests` are in the default plan so a change in either, or a seeder that drifted from its shape, shows in an ordinary run. Those two suites ask for a plan by its SQL and never count plans (a recording is of the whole process, and a task an earlier test left can add to it), and they assert a plan only where the schema leaves SQLite one (a lookup by a unique index, a filter on an attribute with no index), never a choice it makes from cost estimates on a small store, which another SQLite can make the other way. The scale suites were measured on the iOS 27.0 simulator only; CI runs the two default-plan suites on Xcode 26.

## Traps

- The working tree is usually dirty with in-progress work; `git status` before assuming HEAD == working state.
- The working tree routinely carries a large uncommitted change set. Never `git checkout --`, `git stash`, or `git restore` a tracked file to "undo" your own edit — that discards the user's in-progress work, not just yours. Undo your edits in place.
- Cross-actor calls inside **default-argument closure literals** (e.g. `AuthSession.init`'s `cleanupDownloads` / `reopenHTMLContent`, which call `HTMLContentRecoveryService.shared.reopenAccountWork()` and friends) compile *without* `await` and still get their executor hop — under `SWIFT_STRICT_CONCURRENCY = minimal` Swift skips isolation checking in that position, though the same call is a hard error in an ordinary function. Adding the "missing" `await` yields `no 'async' operations occur within 'await' expression`, which `SWIFT_TREAT_WARNINGS_AS_ERRORS` promotes to a build failure. Build before "fixing" one of these.
- CI builds with Xcode 26 (Swift 6.2) and this Mac with Xcode 27 (Swift 6.4), and the two disagree about a memberwise initializer. Under 6.2 a `private var x = value` with no property wrapper is one of its parameters, which makes the initializer private and every use of it from another file an error (`initializer is inaccessible due to 'private' protection level`). 6.4 leaves the property out, so the local build passes and only CI's fails (PR 387's "Build (macOS)"). A view built with its memberwise initializer keeps such state in a property wrapper, which neither compiler makes a parameter: `MacConversationSidebar` reads `@Environment(\.appearsActive)`. `ChatView` can hold a private `WindowAppearsActive` only because it declares its own `init`. They disagree about a `context.perform` block too: one that captures a value of a non-`Sendable` type (`any MessageActionsCoreDataStacking`, say) is an error under 6.2 (`capture of … with non-Sendable type … in a '@Sendable' closure`) and nothing under 6.4, which failed both CI builds of PR 444. Hand the block a `@Sendable` closure made outside it, as `MessageActions.makeBackgroundSave` does.
- Web e2e builds its own demo-mode server (`build:e2e` + `preview --port 4173 --strictPort`) and never reuses an existing one. A stray process on 4173 therefore kills the run at webServer startup with a port-in-use error — kill it rather than debugging fixtures. Demo mode comes from `web/.env.e2e` blanking `VITE_GOOGLE_CLIENT_ID`; a non-demo build would fail every test on a missing fixture, which is why reuse is disabled.
- `web/.env`, `web/.env.e2e`, and `esc-chatmail/Configuration/{Debug,Release}.xcconfig` are tracked on purpose — public client identifiers, not leaked secrets. Do not remove or relocate them.
- Do not add a live `@FetchRequest`/FRC to `ConversationListView` — an always-on FRC re-diffed the whole result set on every merged sync save. The view model's `objectsDidChange` pipeline owns live updates.
- `docs/archive/` (`consolidation.md`, `decomposition.md`, `performance-reliability-plan.md`, `PR-DESCRIPTION.md`) holds campaign closeouts, not roadmaps, and their file paths predate the ORG1 moves. `consolidation.md`'s "CI cannot go green / 90-minute timeout" claim is stale.
- `ProcessedTextCache` was retired (ORG2; original plan in `docs/archive/consolidation.md`). Chat-bubble text processing lives in `ChatBubbleTextProcessor` (+`HTMLTextExtraction`), `RichContentClassifier`, and `MessageBubbleContentSource` (stored-body loading and cache source signatures); `RenderedMessageCache` is the only in-memory memo for bubble text and rich-content verdicts. The compatibility *derivation* for blank `chatPreviewText` rows remains, but `ChatPreviewRepair` now runs two passes: `receivedHTMLRederivation` (every received row, deriving only where local HTML exists, keyed by `CacheVersioning.chatPreviewDerivationVersion`) and `blankPreviewBackfill`. The backfill stores exactly what the bubble already showed, from local sources only, and deliberately leaves two populations blank: forwarded subjects (a stored preview replaces the forwarded lead-in) and received rows without local HTML (the loader can still recover HTML over the network). Keep `ChatPreviewRepair.backfilledPreview` built from the loader's own shared steps (`MessageBubbleContentSource.processMessage` / `.bodyTextFallback`) so the two cannot drift. `LegacyOutgoingBodyTextFallback` is now backfill-only — the bubble loader no longer compares bodies — and must stay: a device upgrading straight from a pre-backfill build needs this pass to migrate legacy outgoing rows whose `bodyText` is richer than their stored HTML. Passes are independent: one stopping early (a retained failed send defers its conversation indefinitely) must never block the other. Do not reintroduce a second text cache in front of it: every message-content invalidation already reaches `RenderedMessageCache` through `HTMLContentLoader.invalidateContent`, under a generation captured before the eviction.
- The rich-content verdict (text bubble vs preview card) is persisted on `Message.richContentVerdict` so a bubble routes at mount instead of behind the "Loading..." pill. `RichContentVerdictResolver` is its only definition: the bubble loader and every writer evaluate it over the same stored state (on-disk HTML, `bodyStorageURI`, `bodyText`, `snippet`, `isFromMe`), and a stored verdict the load then contradicts shows as a text bubble swapping to a card after mount. So never re-derive the rule at a call site, and never feed it anything but stored state (the persister classifies the trimmed string it saves, not the raw part). The bubble loader memoizes only the classifier term in `RenderedMessageCache`; the own-row and fallback-text terms are evaluated fresh on every load, because the memo's key covers only the HTML candidate. Writers: `MessagePersister.stampRichContentVerdict` (in the row's own save, after its last input is final; an update re-stamps when it saved HTML, which is the only way `bodyStorageURI` changes there, when `isFromMe`, `bodyText` or `snippet` changed even though no HTML arrived, or when the stored verdict is unknown), `RichContentVerdictRefresher` (scheduled by the two non-persister HTML save sites, and by a bubble load whose verdict differs from the stored one), and `RichContentVerdictBackfill` (launch pass, newest first). The other thing a load used to add after mount, a row's shared-document links (their URLs stripped from the bubble text, a card appended for each), is known at mount too: `ChatMessageRowModel.storedSharedDocumentLinks` carries them for non-forwarded rows with a stored preview, and the bubble shows them until its load has published (`MessageDisplayPolicy.sharedDocumentLinks`). The row's links and the load's come from one definition, `SharedDocumentLinkExtractor.bubbleLinks`: change the loader's link inputs and `storedRowLinks` together, or a mounted row re-renders when its load lands. The per-row cost is gated by `SharedDocumentLinkExtractor.mayContainLinks` (a substring check through `NSString`, because the mapper runs per row on the main actor) and memoized on `Message.storedSharedDocumentLinks`; a link whose host is spelled only after normalization (percent-encoded, full-width) is missed by that check, so that row still gains its card after mount. `.unknown` is never a guess at "not rich": an evaluation that could not read stored state (closed account boundary, unreadable file) writes nothing, or unknown where the inputs just changed. The stored value embeds `CacheVersioning.richContentVerdictEpoch`; bump it with any change to `RichContentClassifier` or the cleanup chain feeding it, which makes every stored verdict read as unknown rather than stale. Views read it only through `ChatMessageRowModel.knownRichContentVerdict` (nil for own, forwarded and blank-preview rows, whose loads do not publish this rule's answer), and it must stay out of `MessageBubbleLoadSignatureComponents`: it is an output of the load, and a verdict write must not restart one. The attribute is optional, so a row can hold NULL (the v4→v5 migration wrote 0 into existing rows on the runtime it was tested on, which is Core Data's choice): never filter on it without the `== nil` disjunct.
- The chat transcript's hidden initial-anchor pass (`ChatMessagesCoordinator`) confirms a reveal only with the newest row's view in the hierarchy (`VirtualScrollState.isNewestVisibleRowRealized`, fed by each row's `onAppear` through `markRowRealized` and cleared by its `onDisappear` through `markRowUnrealized`, keyed by the row's `ForEach` identity so it survives the echo swap the view does not remount for), not on anchor geometry alone: the `LazyVStack` can leave the tail unrealized after the anchored jump to the content end while SwiftUI's geometry reads correct, which was "the chat opens blank until I scroll" (`ChatTranscriptRealizationPolicy`). Keep `markRowRealized` in the row's `onAppear` and `markRowUnrealized` in its `onDisappear` (the record is the view's current placement: below iOS 18 the pass anchors size changes at the top, so growth above the tail pushes the newest row off mid-pass), ungated by the anchor hold, and keep a probe that lacks that evidence a real offset change (the second-newest row, then back to the anchor), never a `scrollTo` to the offset the view is already at.
- The transcript's sliding replace keeps the rows on screen (`VirtualScrollWindowPolicy`; architecture review 2026-11, chat-transcript-ui#1). The position (`markIndexVisible`) is the row that appeared last, the bottom edge while scrolling down and the top edge while scrolling up, and its own rows are `bufferSize` above it and `visibleItemCount + bufferSize` from it down, from one configuration on every platform. A viewport showing more rows than that (the Mac's 30-point rows, an iPad) lost on-screen rows from the `ForEach` at every replace. So a load also keeps the realized rows that run on unbroken from the position's rows, and on a side where that run reaches past them up to `bufferSize` rows beyond it, which keeps the window from ending at the viewport's edge (a viewport ending exactly at the position rows' edge keeps none there, as before). Widening starts once more than `bufferSize` rows are realized above the bottom edge while scrolling down, so a phone realizing more than about ten rows widens too, unmeasured on a phone; a wider replace re-maps all its rows on the main actor (about 70 instead of 40 for a Mac viewport of 33 rows). The run is bounded only by the window and the cap, so it relies on `onDisappear` reaching a row that scrolled off: unmeasured on the Mac, and if it did not, every replace would keep the window back to its start and it would grow to `maxWindowSize`. Four things fail silently. Whether a load is needed is decided from the position's rows alone (`positionRows`), and nothing beyond them is kept that the window does not already hold, so the realized rows add no load or prepend. Only the run on from the position's rows counts, never the first and last realized rows: a realized row apart from the screen is a record not yet cleared (an `onDisappear` still to come after a jump, or one never delivered), and keeping it held the window back until the cap. The realization record must stay the view's current placement (`markRowUnrealized` in `onDisappear`), or the run keeps rows that left the screen. And the replay after a keyboard shift reads its prepend check from the same `requestedRows` (`replayHeldVisibleIndex`); today that start equals the position rows' wherever it matters, so no test tells them apart, and the shared definition is what keeps a future change from prepending at rest. Do not make the buffer symmetric or a configuration larger for a tall viewport instead: every replace re-maps its rows on the main actor. A latest window of `visibleItemCount` rows in a viewport taller than that is still shorter than the viewport and cannot be scrolled to load more (measured in a hosted probe, 30-point rows in 1,000 points): that is an open follow-up, not covered here. Pinned by `VirtualScrollWindowPolicyTests` and `VirtualScrollStateTests`' tall-viewport tests; nothing of it has been seen on a Mac or an iPad.
- `ChatMessagesCoordinator` keeps what one hidden pass records in `InitialPass`, which `InitialRevealState.pending` carries, and a post-reveal follow's arm time and growth latch in the cases of `PostRevealBottomFollowState` (`BottomFollow`; the latch in `.checkingAfterScroll` alone). State that belongs to one pass or one follow goes there, never in a stored property of the coordinator, which has to be reset by hand at every site where a pass or a follow starts or ends. `isReadyToShow` is assigned only by `initialRevealState`'s `didSet`. What the view covers, which touches it lets through, what counts as resting at the bottom, and when the virtual window's initial-anchor hold changes are decided by `ChatTranscriptPresentationPolicy`: `ChatMessagesView` applies its answers and does not combine `initialLoadPhase` and `isReadyToShow` itself.
- A view presented as a sheet needs three things on the Mac, or it traps the window or loses work. It is presented with `appSheet(isPresented:mac:…)` or `appSheet(item:mac:…)`, never SwiftUI's own `sheet` (`AppSheetSourceTests` fails on one outside an `#if os(iOS)` branch): `mac:` is its `MacSheetChrome`, required because the app's sheets ask for no size, and an unsized one comes up as an empty strip 80 points tall that still blocks the window and Quit. A `MacSheetSize` has one width, and the chrome's frame allows no other (`MacSheetChromeModifier`): the Mac offers a sheet 470 points of width, so a width given as a minimum and an ideal opened 470 wide or at the minimum, never the ideal. Never size a sheet with `presentationSizing` instead (`AppSheetSourceTests` fails on a call): fitted to the content it lays the sheet out twice as it opens, which stops the reader adopting a pre-rendered WebView, makes the sheet's window resizable, and leaves a sheet that follows another on one presenter with the first one's size. An `appSheet(item:)` whose item is replaced by another before SwiftUI's next update is not ended on the Mac: its window stays and the next item's content is drawn in it (Participants, then New Contact), `onDismiss` is not called, and an `onAppear` on the view the content closure returns does not run again. So a presenter that keeps track of the item on screen takes it from `appSheet(item:)`'s `onItemShown:` and from nothing else, as `ChatView` does for `presentedSheetDestination`, never from an `onAppear` of its own on the content (`View.onSheetItemShown`): tracked that way the chat took Participants for the sheet on screen, refused every dismissal of New Contact as a replacement's (`ChatSheetDismissalPolicy`), and neither of that sheet's buttons closed it (build 562, 2026-11-15). - That menu's Open hands the attachment to the app the Mac has for its kind (`MacAttachmentOpener`; `docs/mac-app-plan.md`, "Files"), and the file is the sender's, so three rules hold it. The kinds that open are named in `AttachmentOpenPolicy` and nothing else opens: images, audio, video and PDFs by family, and text and document types as themselves, by identifier. Never add `.plainText` as a family (every script, `run.command` included, conforms to it), never drop the SVG refusal (an image by conformance that opens in the browser with its script) or the refusal of text inside the families (the system files Windows Media's redirectors, `.wax` and `.wvx`, under sound and film, and each is an XML list of addresses for a player to fetch; RealAudio is refused whole because a `.ram` link file has the sound's own type), and never decide by the email's MIME type: the system picks the app by the last extension of the name the file is opened under, so that is what is asked. The menu has no Open for any other kind, and the opener asks the rule again before it opens anything. What opens is a read-only copy under the attachment's cleaned name (`AttachmentOpenCopy`), never the stored file, which another app could write into (Preview saves a markup in place). The copies are account data and live in `Attachments/Opened/`, the directory sign-out and the fresh-install handler remove whole, `AccountScopedMailboxFileInspector.hasStoredFiles` counts and the orphan sweep clears: never put them in the temporary directory, never make one outside a registered operation of `AttachmentAccountWorkRegistry` (sign-out drains that registry before it removes `Attachments`, and a copy in a bare `Task.detached` could land in the directory while it is removed, or after; an Open the sign-out overtook opens nothing and says nothing), keep `AttachmentOpenCopy.markInUse` on every copy handed out, the one made before included (the sweep reads the `Opened` folder's own dates, which a reused copy does not move), and never lock them with the user-immutable flag in place of the 0444 permission, because removing a directory fails on a locked file inside it and sign-out's removal of `Attachments` would fail. `NSWorkspace` is behind a closure, and no test may launch an app. Nothing has been opened in the app: whether the sandbox lets `NSWorkspace` hand another app a file from the container has not been seen.
- An attachment in the Mac's chat that has its file can be dragged out, as a file promise under that same cleaned name (`MacAttachmentFilePromiseProvider`): the stored file's URL would arrive in the Finder under its storage name, and a renamed copy in the container would be account data that sign-out does not know about. The drag source is an AppKit view over the attachment (`MacAttachmentDragSourceView`, `View.macAttachmentDragSource`), not `onDrag`, and three things go with it. It takes the left mouse button, so it hands a click on to the attachment's Quick Look and is only over an attachment that `isReady`: put it over a failed one and the retry control is unreachable. It is put there when the row is drawn, so its `hitTest` asks again at every press and answers nil once the attachment has lost its file. It is applied before `macAttachmentExportMenu`, so the menu's view contains it and its `menu(for:)` finds the attachment's menu behind it. And its dragging session is started through `beginSession`, which every test replaces: never start a real session in a test, it is the window server's and follows the user's pointer. Drops are allowed outside the app only. Measured in the test host with events handed to the view; no drag has been made in the app.
- Mac behaviors that are decisions, not gaps to close (Kevin, 2026-11-11; `docs/mac-app-plan.md`, decisions 5 to 8). Closing the window quits the app, so do not make the `Window` scene a `WindowGroup` or add a delegate that keeps the app running. SwiftUI quits an app whose one `Window` closes, but not while the Settings window is open (measured in a stand-in program: it ran on with only Settings), so `MacAppDelegate` also quits when the window whose identifier is `MacMainWindowPolicy.windowID` closes (`MacMainWindowCloseObserver`). That quit is asked for from the run loop (`perform(_:with:afterDelay:)`), never from `DispatchQueue.main.async` or a `Task`: `applicationShouldTerminate` holds a quit for a send in flight and answers from a main-actor task, and `terminate(_:)` called from a main-queue block waits inside it for an answer the queue can then never run, which hung the stand-in for good (`MacSettingsSceneSourceTests`). The first click in an inactive window only activates it: `LayoutAwareWKWebView` does not override `acceptsFirstMouse(for:)`, so that click cannot follow a link in the reader. A new install starts with about five minutes of mail, as on iOS, and so does every sign-in after a sign-out; nothing loads older mail. Compose has no From: alias picker on either platform.
