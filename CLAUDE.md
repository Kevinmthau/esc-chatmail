# CLAUDE.md

Native iOS SwiftUI Gmail client (chat-style mailbox) plus a separate `web/` PWA. `AGENTS.md` and `CONCURRENCY.md` are the pre-existing agent docs; this file does not replace them.

## Build, test, lint

Always use the wrappers: they resolve an installed `iPhone 17 Pro` by device ID (newest available runtime), respect an explicit `DESTINATION`, export `DEVELOPER_DIR` to the Xcode app toolchain (plain `xcodebuild` otherwise resolves to Command Line Tools), and `cd` to the repo root. `Scripts/run-tests.sh` run bare works but auto-picks the first available iPhone simulator, sets no `DEVELOPER_DIR`, and passes no `-project`.

```bash
export "$(bash Scripts/prepare-simulator.sh)"       # boots a sim + pre-grants Contacts, pins DESTINATION to it
./Scripts/codex-build.sh                            # xcodebuild build, Debug, iPhone 17 Pro sim
./Scripts/codex-test.sh                             # full suite, default test plan (esc-chatmail.xctestplan)
./Scripts/codex-test.sh -only-testing 'esc-chatmailTests/SyncRunCoordinatorTests'
./Scripts/codex-test.sh --performance               # Performance.xctestplan: PerformanceRegressionTests only
./Scripts/codex-test.sh -parallel-testing-enabled NO # escape hatch for the Core Data parallel flake
./Scripts/lint.sh                                   # SwiftLint, advisory; silently exits 0 if swiftlint isn't installed
```

## Layout

- `esc-chatmail/` is the app target; `Services/` holds nearly all logic, with Sync, Send, Caching, HTMLContent/HTMLSanitization, EmailDOM (SwiftSoup) and Chat the dense areas.
- Entity classes: `Services/CoreData/ManagedObjects.swift` (`@objc` class decls) + `Services/Models/<Entity>+Extensions.swift` (`@NSManaged` props, helpers). Exceptions, whose `@NSManaged` props are declared in `ManagedObjects.swift` itself: `ChatReplyDraft` and `OutboundSendMutationRecord` (neither has a `+Extensions` file) and `Attachment.replyDraft`. Adding an attribute means editing the versioned `.xcdatamodel` **and** the file holding that entity's `@NSManaged` props.
- `esc-chatmail/Models/` holds the versioned schema (`esc-chatmail/Models/CoreData/ESCChatmail.xcdatamodeld`, current version `ESCChatmail 6.xcdatamodel`; a schema change is a new version directory plus the `.xccurrentversion` bump, never an edit to a shipped version, whose hashes on-device stores carry) plus a legacy grab-bag of value types; entity *class* code is not there.
- Test directories broadly track `Services/` subsystem names but are not a strict mirror; shared fakes live in `esc-chatmailTests/TestSupport/` (`Mocks/`, `Builders/`, `TestCoreDataStack.swift`, `FakeSyncClock.swift`).
- App and unit-test targets use filesystem-synchronized groups: new `.swift` files are picked up automatically. Never hand-edit `project.pbxproj`.
- `web/` is an independent React/Vite/Dexie PWA in no Xcode target. Its only contract with iOS is the golden corpus, imported live via the `@fixtures` alias — editing `esc-chatmailTests/TestSupport/Fixtures/**` triggers web CI.

## Account-generation boundary (break this and data leaks across accounts)

Every account-scoped subsystem is fenced by an admission flag plus a monotonic generation — roughly two dozen participants today; enumerate them with `grep -rn 'func reopenAccountWork\|func reopenAdmission' esc-chatmail/` rather than trusting a number here.

- **All orchestration lives in `AuthSession`** (`Services/Security/AuthSession.swift`). Four entry paths (`restorePreviousSignIn`, `signIn`, `signOut`, `signOutAndDisconnect`) serialize on a FIFO auth-transition gate (`beginAuthenticationTransition`/`endAuthenticationTransition`); the crash-resume pair (`resumeInterruptedAccountRemovalIfNeeded` / `resumeInterruptedCredentialCleanupIfNeeded`) deliberately takes no gate of its own — it runs inside `restorePreviousSignIn`'s ownership and must never gain another caller. All six then follow one fixed order: `outboundTaskRegistry.closeAdmission()` → `syncRunCoordinator.beginQuiescence()` → `cancelAndAwaitAll()` → `cleanupDownloads()` → destructive cleanup → reopen → `endQuiescence()` → only then publish authenticated UI. Gate-vs-close ordering differs by direction, deliberately: `signOut`/`signOutAndDisconnect` persist the durable reset marker and call `closeAdmission()` synchronously **before their first await** (so a queued sign-out's intent survives even while an earlier transition owns the gate), then wait on the gate; `signIn`/`restorePreviousSignIn` take the gate **first** and close admission once they own it — a queued sign-out supersedes them via `isAccountRemovalRequested` re-checks at the destructive-cleanup and reopen checkpoints (**not** after every await: the seam between `endQuiescence()` and publishing authenticated UI has no re-check, so a sign-out landing there sees a flash of authenticated UI that it immediately tears down — accepted as cosmetic). The gate has no reentrancy detection and gate waits are uncancellable (`withCheckedContinuation`): never start a second transition from inside one.
- A new participant must be wired into `AuthSession`'s six injectable closures (`cleanupHTMLContent` / `reopenHTMLContent` / `cleanupDownloads` / `reopenDownloads` / `resetPendingActionRetryState` / `pendingActionAuthenticationDidRecover`), or into `HTMLContentLoader.closeAccountWorkAndClearCaches()`'s fan-out. Otherwise it never closes. Any new AuthSession path that publishes an authenticated session must call `pendingActionAuthenticationDidRecover` — the pending-action queue's revoked-credential park is released only there, and a forgotten hook parks the queue until process restart. Plain account-scoped state with no work to drain (`SyncEngine`'s full-disk backoff and banner) resets through `resetSyncStorageState`, called beside `resetPendingActionRetryState` on every path that calls it.
- Participant contract (duck-typed; there is no shared protocol): `private var acceptsAccountWork`, `private var accountGeneration: UInt64`, `captureAccountGeneration() -> XAccountGeneration?` (nil while closed), `isAccountGenerationCurrent(_:)`, a close method, `reopenAccountWork()`. Define your own nominal token struct — never pass raw integers or another subsystem's token. `MessageBubbleHTMLAnalysisCache` is the smallest complete example.
- Closing must **drain**, not just flip a flag: cancel and `await` every in-flight task before clearing storage. Producer closures retain old-account content even when their final write is generation-rejected. Naming encodes it (`...AndAwait`, `...AndClear`). Reopen guards refuse while work is outstanding, so a leaked task silently keeps the subsystem closed for the next account.
- Caller contract: capture tokens once up front (bail if any capture returns nil), re-validate after **every** await before using or storing a result, and pass `expectedAccountGeneration:` down into async writes. Multi-participant callers build a composite context (`MessageBubbleLoader.captureAccountWorkContext()`).
- Reopen is all-or-none: `AuthSession.reopenAccountWork(after:)` rolls back downloads and HTML if a later reopen step refuses. Anything but `.reopened` means do not publish an authenticated session, and the three refusal cases are **not** interchangeable — `.transientFailure` (a reopen step threw; retry with the same credentials), `.latchedRefusal` (old-account work still outstanding — a refused download reopen or an undrained outbound send reservation; this transition cannot publish and repeating it is not expected to clear the latch; only the outbound cause proves no superseding transition exists — the download cause cannot check, and a sign-out queued mid-reopen behind it converges benignly with the restore's credential discard), `.supersededByAccountRemoval` (a queued sign-out owns the teardown, including its own credential cleanup). `OutboundTaskRegistry.reopenAdmission(after:)` distinguishes those two refusals itself and deliberately reports supersession before undrained sends when both hold — a latched verdict on a stale transition would route a restore into discarding credentials the queued sign-out owns. `AuthRestoreReopenPolicy.restoreDispositionAfterReopen(_:)` owns the outcome→credential-disposition mapping for the restore path; never clear credentials on a cause it maps to `.retryKeepingCredentials`. `reopenPreSignInAccountWork` is deliberately *not* all-or-none: its caller cannot unpublish the session it is restoring, so a refused download reopen degrades (log only) and outbound admission still reopens; an undrained-sends outbound refusal likewise degrades (send latch only), and only genuine supersession rolls back. Reopen must also recreate directories cleanup deleted (`AttachmentPaths.setupDirectories()`, Messages dir, preview cache dir).
- Restore and sign-in additionally gate on `prepareLocalStoreForAuthenticatedAccount(_:)`, held under the account-transition lease: the app owns **one** account-wide store and conversations carry no account predicate, so a matching `Account` row is not sufficient (any other surviving row forces a reset) and an absent row is safe only when the mailbox store *and* the canonical HTML directory are genuinely empty. Never publish authenticated UI before it returns; failure maps to `AuthError.localAccountIsolationFailed`.
- `TokenManager` runs its **own** sign-out generation, separate from these fences. `cacheLock` guards the cached token pair, the epoch, **and** both writers' keychain writes/deletes, so `saveTokens`/`clearTokens` can never interleave keychain operations; **both** `clearTokens` and ungated `saveTokens` (sign-in/restore via `persistSessionForBackgroundAccess`) bump the epoch inside that section — any future ungated `saveTokens` call site therefore silently cancels in-flight refreshes, by design. Any new token-producing path must snapshot the epoch *before* its unserialized keychain read or network call, publish only via `setCachedToken(_:ifEpochMatches:)`, and after the MainActor hop re-check that the epoch still matches **and** the cached token equals the one being published before assigning `authSession.accessToken` — a bare `cachedToken() != nil` is insufficient now that ungated saves bump the epoch, because a replacement account's freshly cached token would pass it and a retired publish would overwrite the replacement's session state. Refresh single-flighting is `TokenRefreshCoordinator`, keyed on that epoch: a refresh whose generation was retired throws `CancellationError` rather than returning a token, overwriting replacement tokens, or publishing a revocation verdict into the replacement session — callers must not expect a token-once grace delivery after sign-out.
- `CacheCoordinator` captures the generation on the **posting** context's queue inside the didSave publisher, before `.receive(on: .main)`. Any new notification-driven invalidation must capture at post time, not delivery time.
- Interactive local mutations (mark read, pending actions) use the **non-exclusive** lease: `makeAccountWorkRequest()` → `acquireAccountWorkLease(kind:for:)` → work → `isActiveRun(_:)` re-check after each suspension → `endRun(_:)`. A lease holder must **never** wait on the exclusive boundary (`waitUntilIdle`/`beginRun`/`acquireRun`) before releasing — teardown drains leases, so that deadlocks. `acquireAccountWorkLease` deliberately ignores `Task.isCancelled`.
- Add boundary regression tests next to `AuthSessionTests` / `HTMLContentAccountBoundaryTests`; the standard shape is "stale generation is rejected after reopen".

## Sync cursor and staging invariants

`SyncEngine` is a facade over `InitialSyncOrchestrator` / `IncrementalSyncOrchestrator`, gated by `SyncRunCoordinator` (single-flight).

- **Nothing but the orchestrator's own save points may save the sync context.** `SyncFailureTracker`, both checkpoint stores, and `AccountPersister.setAccountHistoryId` stage into the caller's context so the failure ledger, the durable counter, the continuation token, and the Account cursor commit or die together.
- Advance the Account `historyId` only when `planHistoryAdvance` returned `shouldAdvance` **and** the history slice is terminal (`nextPageToken == nil`). A truncated slice stages the continuation token and leaves the cursor frozen; a non-advancing slice moves neither.
- Apply `SyncFailureTracker` success-side effects only via `commit(_:)` **after** the final save succeeded; discard the plan on save failure. Never call `recordSuccess()`/`reset()` inside a run.
- Account-scoped aborts (`APIError.isAccountScopedSyncAbort`: auth, revoked credentials, quota) are run-level: put the IDs in **no** failure bucket, stop issuing requests, rethrow so nothing commits.
- Every attempted ID lands in exactly one `MessagePersistDisposition` bucket (persisted / excluded / unprocessable / failed). Only `.failed` and fetch failures freeze the cursor; 404s and deliberate exclusions must not.
- `MessageProcessor.processGmailMessage` encodes the body-materialization contract in *whether it throws*: a thrown error means content could not be fully materialized and the message **must not be persisted as-is** — callers map it to a blocking per-message failure (or a run abort for account-scoped errors) so the cursor cannot advance past a silently body-less row. Deterministic per-part failures (404, undecodable response) deliberately do **not** throw, because retrying cannot materialize the part; the best-effort embedded-HTML salvage probe never throws either (except account-scoped failures and cancellation). Classify any new body/attachment error into one of those three buckets explicitly.
- Cancellation always propagates as a thrown error and is never recorded as a per-message verdict — a partial partition would look like a clean batch.
- A failed Core Data read is never "absent"/"empty": `planHistoryAdvance` returns `.held` when the ledger is unreadable even on an otherwise clean run; lookup failures return `.lookupFailed`/`.failed` rather than creating duplicates or advancing.
- `recordFailure` **replaces** the deferred set and must never truncate; a staging failure latches `deferredStagingFailed`, which blocks the escape hatch.
- Ledger states have different retry owners: `deferred` rows are retried by the normal re-scan (excluded from the drain); `abandoned` rows only by the drain, which alone owns `retryCount`. Drain failures must never influence cursor advancement. The drain query's `state == nil` / `nextRetryAt == nil` disjuncts are load-bearing on SQLite.
- Background (BGTask) sync uses the same model-v3 executor and cursor/checkpoint rules as foreground sync. `BackgroundSyncManager` owns bootstrap/auth admission, expiration propagation, and retry scheduling; it must not write cursors independently. Keep `BackgroundSyncStateManager.clearContinuationState(in:)` at upgrade and account teardown boundaries to delete checkpoints left by the retired delta writer.
- The incremental path keeps its `UserDefaults` state (`lastSuccessfulSyncTime`, `installTimestamp`, `lastReconciliationTime`, the missed-message cursor) in an injected store, `.standard` by default: `IncrementalSyncOrchestrator(defaults:)`, which hands it to `ReconciliationPhase` and `SyncTimeCalculator`, `SyncReconciliation(defaults:)` and `SyncFailureTracker(defaults:)`. All three must be given the same store, because the tracker writes the last-sync time that the orchestrator's recovery and the reconciliation window read. `InitialSyncOrchestrator` still reads `.standard` directly.
- Recompute and save conversation rollups inside one `ConversationRollupMutationSerializer.performThrowingSyncMutation` block keyed on the affected conversation IDs.
- Every run opens a `ModificationTracker` transaction and must commit+consume on success or roll back on every error path.
- `MessagePersister.saveMessages`: preparation is concurrent and writes nothing; persistence is strictly sequential in the caller's order, so callers pass chronologically sorted messages.
- Suites that pin all of this: `IncrementalSyncCursorTests`, `SyncFailureTrackerEscapeHatchTests`, `ForegroundHistoryCheckpointStoreTests`, `SyncFailureCounterCheckpointStoreTests`, `SyncRunCoordinatorTests`, `MessagePersisterDispositionTests`, `AbandonedMessageRetryTests`. Extend them for any sync change.

## Outbound send (non-idempotent; never resend)

- Gmail `messages.send` has no idempotency key. `sendMessage` uses `allowsRetransmission: false`. Never route a send onto a retrying/idempotent path.
- The transmission-admission barrier is `try Task.checkCancellation()` + `try await beforeTransmission()`, the last safe point before URLSession admits the request. New work goes **before** it, never between it and the request.
- Outcome matrix keys off `TransmissionBarrierState.isPersisted`: pre-barrier failure → the request's `PreTransmissionFailureDisposition`. `.rollBackToComposer` (ComposeView compose/forward, whose composer keeps the content until admission) rolls back the optimistic message + fails admission; `.retainAsNotSent` (chat replies: `sendReply` clears the field at tap and releases the composer at `onOptimisticMessagePersisted`) retains it as definitely-unsent + succeeds admission, writing no `ChatReplyDraft` and requeuing nothing (the composer may already hold the next reply). Pre-barrier cancellation, ambiguous errors and account teardown (`teardownRequested`) always roll back; background-time expiry before the barrier is not a teardown and follows the disposition (`backgroundTimeExpiredWithoutTeardown`), so an offline reply parked in `OutboundConnectivityGate` when the phone locks stays "Not sent". A rollback *merges* a reply into `ChatReplyDraft` (`saveMergingUnsentReply`, never `save`: the slot may hold the next reply); one that cannot write the draft retains the row instead and reports `PreTransmissionRollbackOutcome.retainedAsNotSent`, which must succeed admission, or the composer restores text the bubble still shows. It restores pre-send archive state only if `archiveStateIsOptimisticOnly` (read before the rollup recompute): an archive made during preflight wins. Deterministic refusals (no recipients, threadless reply) belong before optimistic creation, or a Not-sent row would fail the same way on Edit and resend. Post-barrier ambiguous/cancellation → `recordAmbiguousRemoteSend` + succeed (graph retained, no retry); post-barrier definite rejection → retain as definitely-unsent. Misclassifying a new error class is a duplicate-send hazard. Ambiguous = CancellationError, serverError, timeout, decodingError, non-pre-transmission networkError.
- The deterministic RFC Message-ID (`MimeBuilder.messageId(forOptimisticMessageID:)`) is how sync matches the echo. Always pass `messageId:` on outbound calls; dropping it silently breaks convergence.
- Optimistic conversation hashing must use `AliasManager.shared.getAliases(from: viewContext)` — the context-taking overload, never a cache-only read. It falls back to Core Data when the alias cache is cold (fresh launch, post-invalidate), which is exactly when a self-exclusion miss would hash the optimistic conversation differently from the synced-back echo and fork the chat.
- Inserting an optimistic outgoing message bumps `lastMessageDate` and `snippet` only. Do **not** set `conversation.hasInbox = true` — an outgoing message is not inbox presence, and setting it resurrects archived chats on send.
- On API success, do **not** rename or delete the optimistic row. Sync owns atomic replacement and record consumption (`remoteCommittedSendMutationResolutions` / `consumeRemoteCommittedSendMutation`), inside the same transaction that persists the echo.
- Any conversation merge, dedup, or cleanup pass must exclude conversations named by an in-flight `OutboundSendMutationRecord` (`ConversationMerger` fetches those `conversationId`s and skips them). The optimistic message may still be unsaved on the view context and therefore invisible to a background fetch; deleting its conversation as a merge loser orphans it and dangles the reconciliation record. Same reason `GmailSendService` refuses to anchor an optimistic reply to a deleted or `isRetainedDrainedShell` conversation.
- `missingRecordIsError` is true only for `recordRemoteSendAdmission`; other marker writes must tolerate a record an echo already consumed.
- There is no user-facing resend affordance. Cold recovery (`reconcileAbandonedOptimisticSendMutations`) never retries — it only converts markers.
- Sends flow `reserve()` → `ownPreparation` → `handOff` → `admitTransmission` (the linearization point; after it the send is drain-only). Re-check `isActive(reservation)` after suspensions.
- A reply's `ChatViewModel` can outlive its screen (navigation stays open during a send; the send task retains it). `ChatReplyComposerDirectory` makes the newest presented composer the only writer of the conversation's draft; an off-screen model hands an unsent reply to the open composer or merges it into the stored draft (`returnUnsentReply`), never restores it into itself. A composer that left the screen saves through the cleanup gate, so its save can still be waiting when the chat is opened again (on the Mac, chat A, B, A on arrow keys): the new composer then takes the draft from it in place of the stored one (`handOverOwedReplyDraft`, found through `withdrawnDraftOwner`) and makes the save itself. Only a composer that still owes a save gives its draft (`replyDraftSaveIsOwed`; one that owes nothing can hold less than the store, which may have had an unsent reply merged in), never one that is sending, and only finalized attachments go. Every scheduled draft save must start in `startReplyDraftSave`, or the flag misses it and that draft is lost as before. `ChatView` must keep calling `composerDidAppear`/`composerDidDisappear`. From tap until the reply has a durable owner again the send holds a `ChatReplyComposerDirectory.UnpersistedSend`; while one is held the stored draft is still the reply being sent, so a composer created meanwhile must not restore it (`restoreReplyDraft`), and every exit path must `end()` it (a leak disables draft restore for that chat until relaunch).
- Chat replies to one conversation transmit in tap order: the worker awaits its `OutboundConversationSendSequencer` turn strictly before the barrier, so a queued send is still a preflight registry entry that `closeAdmission` cancels (the wait is cancellation-aware). Any terminal predecessor (succeeded, failed, ambiguous, cancelled) releases the next; nothing is retransmitted. Every path must `finish()` its turn. Only `.reply` requests take a turn (`OutboundMessageRequest.takesConversationSendTurn`): ComposeView compose and forward hold their sheet until admission, so they neither wait on nor hold the turn and are never parked behind a chat reply's upload.
- Before its turn, the worker runs `OutboundConnectivityGate.waitForUsablePath`: on a known-unsatisfied `NWPath` (only `.unsatisfied`; `.requiresConnection`, e.g. idle VPN On Demand, is activated by the request itself — `OutboundNetworkPathMonitor.isUsable`) it waits (cancellation-aware) up to `NetworkConfig.sendConnectivityWaitTimeout` for the path to return, then fails with a pre-transmission `URLError(.notConnectedToInternet)` that the request's disposition decides. It is the only connectivity wait on the send path (the send session never waits for connectivity) and must stay before the barrier. Tests inject `OutboundNetworkPathMonitoring` and a clock; the shared monitor reports satisfied under hosted unit tests.
- Coverage: `GmailSendServiceOptimisticFailureTests`, `ComposeSendOrchestratorTests`, `OutboundMessageCoordinatorTests`.

## Conventions

- **Concurrency:** `actor` for stateful multi-task services, `@MainActor final class ... : ObservableObject` for view models. `SWIFT_STRICT_CONCURRENCY = minimal` is a ratchet floor; `targeted` does not compile today. `@unchecked Sendable` is a debt marker — carry a `///` comment naming the synchronization that justifies it; grep for the current holders.
- **Core Data:** merge policy `NSMergeByPropertyObjectTrumpMergePolicy` is set by the three `CoreDataStack` factories (viewContext, `newBackgroundContext()`, `performBackgroundTask`); a hand-built context must set it itself, as `GmailSendService+OptimisticUpdates.swift` and `ConversationCreationSerializer.swift` do. Save via `context.saveOrLog(operation:category:)` or `await context.performSaveIfNeeded(caller:)`, not `try? save()`. Keep fetches and mutations inside the owning context’s `perform` closure; use the save helpers in `NSManagedObjectContext+Perform.swift` where appropriate. Never mutate the loaded `NSManagedObjectModel` at runtime — schema changes go in versioned `.xcdatamodel` files only. `Services/DatabaseMaintenance/SQLiteDatabase.swift` is a thin SQLite handle used only by `DatabaseMaintenanceService+SQLite.swift` for VACUUM, ANALYZE, and REINDEX. Indexing is the 19 `<fetchIndex>` declarations in the current model version — the never-called raw-SQL index/pragma setup that used to sit beside `SQLiteDatabase` was deleted; do not reintroduce hand-written SQL against Core Data's Z-tables.
- **Managed objects never cross context or actor boundaries.** Pass `NSManagedObjectID`, re-resolve on the destination context, map to `Equatable` value snapshots (`ChatMessageRowModel`) for SwiftUI.
- Message bodies and attachments live on disk, not in Core Data. Route body-file access through `HTMLContentHandler` (process-wide account boundary), never raw `FileManager`. Never read `Attachment.localURL` / `previewURL` directly for rendering or opening — use `readableLocalURLValue` / `readablePreviewURLValue`; legacy ID-only remote paths and `local_inline_*` files stay persisted only long enough to trigger migration and must never reach a reader, because an attachment-scoped path can be shared by sibling messages. Recovery paths recompute the deterministic ID from *this* message's MIME part (`AttachmentPaths.synthesizedInlinePayloads`) to prove the bytes belong to the row.
- **Conversation keying** is `Conversation.participantHash` from `calculateParticipantHash` (`p|`) or `calculateListConversationHash` (`l|`). Both are marked CANONICAL — never duplicate the hashing. A list (`l|`) title must **never** be derived from a message's sender at creation (senders vary post to post): use the List-Id display phrase — sanitized by `ParsedListId.sanitizedDisplayTitle`, which rejects provider machine tokens (Mailchimp's `<token>mc list`, Brevo bare tokens, base64-of-numeric-id tokens on any domain) — falling back to the normalized List-Id. The one sanctioned sender-derived exception is the rollup upgrade: a stored identifier-derived title upgrades to the single distinct sender's From name (`ConversationRollupUpdater.updateDisplayNameOnly`). Stored list titles are re-evaluated every launch (`ConversationLaunchRepairCoordinator.repairListConversationTitles`), so a `ParsedListId` heuristic improvement ships **without** a `hasRefreshedConversationNames` key bump — the per-launch pass heals stale titles; bumping the key re-derives every conversation's name on every device. Existing-message *repair* must not apply new-arrival epoch semantics — reuse a durable List-Id conversation whether active or archived and leave `archivedAt` untouched (`MessageConversationRouter.existingConversationObjectID`). `Message.strictParticipantSetIdentity(myAliases:)` returns nil when a message has no `MessageParticipant` rows, and nil means **do not re-home**: `senderEmail` alone cannot reconstruct To/Cc. Current optimistic sends persist known From/To rows, but legacy or partially imported row-less messages remain in place rather than being guessed into a note-to-self chat.
- **Participant display order:** a conversation's participants are shown in ascending order of normalized email address (`ConversationParticipantExtractor.participantsInDisplayOrder`): the loaded title, the avatar stack, the Participants sheet and the stored `Conversation.displayName` all walk it, and the address-joined fallback title sorts by the same key (`PersonDisplayNameResolver.fallbackConversationName`). Never show `conversation.participants` in the order the set iterates, which changes from one load to the next (`ConversationParticipantDisplayOrderTests`). This is display only and has no part in `participantHash`. The stored title leaves out the user's own addresses as the loaded one does, read from the stored `Account` row (`ConversationRollupUpdater.storedSelfAddresses`: no Contacts self-aliases, because the stored title reads nothing from Contacts), except where they are the conversation's only other participants.
- **Untrusted URLs from email content:** any fetch of a URL that came out of message HTML (remote images, link previews, Drive metadata) goes through `SSRFGuardingURLSession.shared`, never `URLSession.shared`. That session blocks redirects to private/loopback/link-local/reserved addresses, but it only sees *redirect* targets, so the caller must also reject the initial URL with `PrivateNetworkAddressDetector.isPrivateOrReserved(_:)` (`HTMLRemoteImageAttachmentFallback.isEligibleCandidate` is the reference call site). Both halves are required: public-looking host → 302 → internal IP is the attack the pair exists to close.
- **Logging:** only `Log.debug/info/warning/error(_:category:)` and `Log.diagnostic(_:level:_:category:)` (e.g. `Log.diagnostic(.startup, level: .info, "…", category: .general)`), always with an explicit `category:`. Redaction is a hard rule at the call site (OSLog cannot redact — the pipeline emits `%{public}@`): `Log.redact(email:/address:/url:/error:)`, `Log.hashIdentifier(_:)` for message/thread IDs. Pass errors to `error:`, not string interpolation. `ScopedLogger` (via `LogCategory.sync.logger`) is live and is house style inside `Services/Sync`; prefer it there, `Log.*` elsewhere.
- **DI:** default-valued initializer parameters — `.shared` defaults for services, `@escaping @Sendable` closures for behavior/time (`SyncClock`, `makeBackgroundContext`, `saveContext`). New code takes a narrowed feature bundle from `Dependencies` (`makeChatDependencies()` etc.) rather than reaching for `.shared`. Top-level views get `Dependencies` and `AuthSession` via `@EnvironmentObject` (see `Dependencies.swift`'s own usage doc); child views and services take constructor injection with a `Dependencies.shared` fallback.
- Errors are domain `enum X: LocalizedError` with an `errorDescription` switch and doc comments distinguishing near-identical cases. No release-path `fatalError`.
- Comments here are load-bearing "why" notes recording past bugs and deliberate non-obvious choices. Preserve them; an unexplained deviation reads as a defect. One type per file, large types split as `Type+Facet.swift` with the base file's header enumerating the split. `///` doc comments only.
- View decisions live in pure `enum XPolicy` static-function namespaces so bodies stay declarative and testable.

## Testing

- 100% XCTest — `import Testing` appears nowhere. Names are `test<Subject>_<scenario>_<expectedOutcome>`.
- Use `TestCoreDataStack`; never construct `NSPersistentContainer(name:)` in a test (a second live model breaks `+[NSManagedObject entity]` and crashes fixture builders under parallel testing). It intentionally uses one process-wide model, a lock around container creation, a private-queue "viewContext", and a never-deallocated graveyard. Save via `stack.saveViewContext()`, never a bare off-queue `context.save()`. `.sqlite` mode exists for persistent-history tests; automerge is opt-in because it races test bodies.
- A `@MainActor` suite whose code under test touches its context directly (fetch/save/delete with no `perform`) takes `stack.makeMainQueueViewContext()`, never `stack.viewContext` — it is private-queue, so every such access is off-queue, which trapped under `-com.apple.CoreData.ConcurrencyDebug 1` and crashed CI's test runner. Route that suite's fixtures, saves, resets, and assertions through the returned context too (a suite-local `saveViewContext()` and `viewContext.reset()`); `stack.saveViewContext()` / `resetViewContext()` act on a different context. `MainQueueMessageActionsCoreDataStack` is the `MessageActionsCoreDataStacking` wrapper for suites that construct `MessageActions`. Prove any new conversion with the ConcurrencyDebug flag before and after.
- A Mac-plan suite that asks AppKit about a mounted SwiftUI view (a hit test, a right-click's menu, an event handed to a view) mounts it with `MacOffscreenHost` in a window from `makeTestHostWindow()`, and one that needs a message's row around an attachment uses `MacMessageRowStandIn`, which hands its menu entries down as `ChatMessagesView` does; `FileBackedAttachmentFixture` makes an attachment with a file in the test's own directory. Do not write another copy of any of the three in a test file.
- Bound waits by wall-clock deadline with a poll interval — copy the nearest per-suite private `waitUntil(timeout:pollIntervalNanoseconds:condition:)`; there is no shared version in `TestSupport/`. Never wait by a fixed number of `Task.yield()`. Use `FakeSyncClock` for backoff/pacing, not real sleeps.
- Test retry/backoff semantics against the **real** `GmailAPIClient` through `StubURLProtocol` — mock-based retry tests are vacuous. `MockGmailAPIClient` is for everything else.
- Avoid the real Contacts store in tests: inject `contactEmailLoader` / `accessRequester`.
- Anti-masking is house style: tests guarding a fix carry a `Revert-check:` comment naming the production symbol whose removal makes them fail, and a `HONEST SCOPE` comment where a test cannot survive a revert. Revert-check every new regression test hunk-by-hunk.
- Message cleaning / preview routing / newsletter scoring regressions go into `esc-chatmailTests/TestSupport/Fixtures/golden_message_corpus.json`, replayed by `GoldenCorpusReplayTests` in `esc-chatmailTests/Sync/MessageProcessorTests.swift`.
- Isolate tests touching process-global singletons with UUID-suffixed identifiers plus explicit invalidation; there is no automatic global reset.
- Unit tests run hosted in the app process, and `initializeApp()` deliberately no-ops under `RuntimeEnvironment.isRunningUnitTests`. Prefer `CoreDataStack(persistentContainerForTesting:)` over `.shared`.
- There is no UI test target (the never-run `esc-chatmailUITests` and the app's `UI_TEST_MODE` / `UI_TEST_AUTHENTICATED` launch-argument hooks were removed). `PerformanceRegressionTests` runs only under `--performance`.

## Traps

- The working tree is usually dirty with in-progress work; `git status` before assuming HEAD == working state.
- The working tree routinely carries a large uncommitted change set. Never `git checkout --`, `git stash`, or `git restore` a tracked file to "undo" your own edit — that discards the user's in-progress work, not just yours. Undo your edits in place.
- Cross-actor calls inside **default-argument closure literals** (e.g. `AuthSession.init`'s `cleanupDownloads` / `reopenHTMLContent`, which call `HTMLContentRecoveryService.shared.reopenAccountWork()` and friends) compile *without* `await` and still get their executor hop — under `SWIFT_STRICT_CONCURRENCY = minimal` Swift skips isolation checking in that position, though the same call is a hard error in an ordinary function. Adding the "missing" `await` yields `no 'async' operations occur within 'await' expression`, which `SWIFT_TREAT_WARNINGS_AS_ERRORS` promotes to a build failure. Build before "fixing" one of these.
- CI builds with Xcode 26 (Swift 6.2) and this Mac with Xcode 27 (Swift 6.4), and the two disagree about a memberwise initializer. Under 6.2 a `private var x = value` with no property wrapper is one of its parameters, which makes the initializer private and every use of it from another file an error (`initializer is inaccessible due to 'private' protection level`). 6.4 leaves the property out, so the local build passes and only CI's fails (PR 387's "Build (macOS)"). A view built with its memberwise initializer keeps such state in a property wrapper, which neither compiler makes a parameter: `MacConversationSidebar` reads `@Environment(\.appearsActive)`. `ChatView` can hold a private `WindowAppearsActive` only because it declares its own `init`.
- Web e2e builds its own demo-mode server (`build:e2e` + `preview --port 4173 --strictPort`) and never reuses an existing one. A stray process on 4173 therefore kills the run at webServer startup with a port-in-use error — kill it rather than debugging fixtures. Demo mode comes from `web/.env.e2e` blanking `VITE_GOOGLE_CLIENT_ID`; a non-demo build would fail every test on a missing fixture, which is why reuse is disabled.
- `web/.env`, `web/.env.e2e`, and `esc-chatmail/Configuration/{Debug,Release}.xcconfig` are tracked on purpose — public client identifiers, not leaked secrets. Do not remove or relocate them.
- Do not add a live `@FetchRequest`/FRC to `ConversationListView` — an always-on FRC re-diffed the whole result set on every merged sync save. The view model's `objectsDidChange` pipeline owns live updates.
- `docs/archive/` (`consolidation.md`, `decomposition.md`, `performance-reliability-plan.md`, `PR-DESCRIPTION.md`) holds campaign closeouts, not roadmaps, and their file paths predate the ORG1 moves. `consolidation.md`'s "CI cannot go green / 90-minute timeout" claim is stale.
- `ProcessedTextCache` was retired (ORG2; original plan in `docs/archive/consolidation.md`). Chat-bubble text processing lives in `ChatBubbleTextProcessor` (+`HTMLTextExtraction`), `RichContentClassifier`, and `MessageBubbleContentSource` (stored-body loading and cache source signatures); `RenderedMessageCache` is the only in-memory memo for bubble text and rich-content verdicts. The compatibility *derivation* for blank `chatPreviewText` rows remains, but `ChatPreviewRepair` now runs two passes: `receivedHTMLRederivation` (every received row, deriving only where local HTML exists, keyed by `CacheVersioning.chatPreviewDerivationVersion`) and `blankPreviewBackfill`. The backfill stores exactly what the bubble already showed, from local sources only, and deliberately leaves two populations blank: forwarded subjects (a stored preview replaces the forwarded lead-in) and received rows without local HTML (the loader can still recover HTML over the network). Keep `ChatPreviewRepair.backfilledPreview` built from the loader's own shared steps (`MessageBubbleContentSource.processMessage` / `.bodyTextFallback`) so the two cannot drift. `LegacyOutgoingBodyTextFallback` is now backfill-only — the bubble loader no longer compares bodies — and must stay: a device upgrading straight from a pre-backfill build needs this pass to migrate legacy outgoing rows whose `bodyText` is richer than their stored HTML. Passes are independent: one stopping early (a retained failed send defers its conversation indefinitely) must never block the other. Do not reintroduce a second text cache in front of it: every message-content invalidation already reaches `RenderedMessageCache` through `HTMLContentLoader.invalidateContent`, under a generation captured before the eviction.
- The rich-content verdict (text bubble vs preview card) is persisted on `Message.richContentVerdict` so a bubble routes at mount instead of behind the "Loading..." pill. `RichContentVerdictResolver` is its only definition: the bubble loader and every writer evaluate it over the same stored state (on-disk HTML, `bodyStorageURI`, `bodyText`, `snippet`, `isFromMe`), and a stored verdict the load then contradicts shows as a text bubble swapping to a card after mount. So never re-derive the rule at a call site, and never feed it anything but stored state (the persister classifies the trimmed string it saves, not the raw part). The bubble loader memoizes only the classifier term in `RenderedMessageCache`; the own-row and fallback-text terms are evaluated fresh on every load, because the memo's key covers only the HTML candidate. Writers: `MessagePersister.stampRichContentVerdict` (in the row's own save, after its last input is final; an update re-stamps when it saved HTML, which is the only way `bodyStorageURI` changes there, when `isFromMe`, `bodyText` or `snippet` changed even though no HTML arrived, or when the stored verdict is unknown), `RichContentVerdictRefresher` (scheduled by the two non-persister HTML save sites, and by a bubble load whose verdict differs from the stored one), and `RichContentVerdictBackfill` (launch pass, newest first). The other thing a load used to add after mount, a row's shared-document links (their URLs stripped from the bubble text, a card appended for each), is known at mount too: `ChatMessageRowModel.storedSharedDocumentLinks` carries them for non-forwarded rows with a stored preview, and the bubble shows them until its load has published (`MessageDisplayPolicy.sharedDocumentLinks`). The row's links and the load's come from one definition, `SharedDocumentLinkExtractor.bubbleLinks`: change the loader's link inputs and `storedRowLinks` together, or a mounted row re-renders when its load lands. The per-row cost is gated by `SharedDocumentLinkExtractor.mayContainLinks` (a substring check through `NSString`, because the mapper runs per row on the main actor) and memoized on `Message.storedSharedDocumentLinks`; a link whose host is spelled only after normalization (percent-encoded, full-width) is missed by that check, so that row still gains its card after mount. `.unknown` is never a guess at "not rich": an evaluation that could not read stored state (closed account boundary, unreadable file) writes nothing, or unknown where the inputs just changed. The stored value embeds `CacheVersioning.richContentVerdictEpoch`; bump it with any change to `RichContentClassifier` or the cleanup chain feeding it, which makes every stored verdict read as unknown rather than stale. Views read it only through `ChatMessageRowModel.knownRichContentVerdict` (nil for own, forwarded and blank-preview rows, whose loads do not publish this rule's answer), and it must stay out of `MessageBubbleLoadSignatureComponents`: it is an output of the load, and a verdict write must not restart one. The attribute is optional, so a row can hold NULL (the v4→v5 migration wrote 0 into existing rows on the runtime it was tested on, which is Core Data's choice): never filter on it without the `== nil` disjunct.
- The chat transcript's hidden initial-anchor pass (`ChatMessagesCoordinator`) confirms a reveal only with the newest row's view in the hierarchy (`VirtualScrollState.isNewestVisibleRowRealized`, fed by each row's `onAppear` through `markRowRealized` and cleared by its `onDisappear` through `markRowUnrealized`, keyed by the row's `ForEach` identity so it survives the echo swap the view does not remount for), not on anchor geometry alone: the `LazyVStack` can leave the tail unrealized after the anchored jump to the content end while SwiftUI's geometry reads correct, which was "the chat opens blank until I scroll" (`ChatTranscriptRealizationPolicy`). Keep `markRowRealized` in the row's `onAppear` and `markRowUnrealized` in its `onDisappear` (the record is the view's current placement: below iOS 18 the pass anchors size changes at the top, so growth above the tail pushes the newest row off mid-pass), ungated by the anchor hold, and keep a probe that lacks that evidence a real offset change (the second-newest row, then back to the anchor), never a `scrollTo` to the offset the view is already at.
- A view presented as a sheet needs three things on the Mac, or it traps the window or loses work. It is presented with `appSheet(isPresented:mac:…)` or `appSheet(item:mac:…)`, never SwiftUI's own `sheet` (`AppSheetSourceTests` fails on one outside an `#if os(iOS)` branch): `mac:` is its `MacSheetChrome`, required because the app's sheets ask for no size, and an unsized one comes up as an empty strip 80 points tall that still blocks the window and Quit. A `MacSheetSize` has one width, and the chrome's frame allows no other (`MacSheetChromeModifier`): the Mac offers a sheet 470 points of width, so a width given as a minimum and an ideal opened 470 wide or at the minimum, never the ideal. Never size a sheet with `presentationSizing` instead (`AppSheetSourceTests` fails on a call): fitted to the content it lays the sheet out twice as it opens, which stops the reader adopting a pre-rendered WebView, makes the sheet's window resizable, and leaves a sheet that follows another on one presenter with the first one's size. A sheet with no control of its own to close it (the email reader, swiped down on iOS) takes `.sizedWithDoneBar`; with no button and no focused text field, Escape does not close a Mac sheet. Its toolbar buttons go at `ToolbarItemPlacement.sheetLeadingBarEdge` / `sheetTrailingBarEdge`, never `leadingBarEdge` / `trailingBarEdge`: a Mac sheet has no toolbar and draws nothing placed at `.navigation`, `.primaryAction` or `.principal`. It does draw a `navigationTitle`, so a title shown as a principal item needs `macSheetNavigationTitle(_:)` (nil for a view that draws its own: an empty navigation title draws an empty strip). A Send button at the trailing sheet placement is the Mac's default button, which a bare Return presses; give it `macSendKeyboardShortcut()`. A Done there answers Return only; `macSheetClosesOnEscape()` adds Escape. And a sheet with a text field: Escape closes it by itself while the field has the focus, pressing no button, so `ComposeView` disables interactive dismissal on the Mac and its Cancel asks before discarding the user's edits (`ComposeCancelPolicy`). `ChatDestination+MacSheet` holds the chat sheets' choices. The Mac has no Settings app page either: it signs out from the app menu's Sign Out… command (`SignOutCommands`) or the same command as a button in its Settings window (`MacSettingsView`, a `Settings` scene). The window has a `SettingsAppSignOutController` of its own, so its confirmation is an alert on the Settings window, and it publishes the menu command too (`signOutMenuAction`), or the command would be disabled whenever Settings is in front. Its content waits for `isInitialized`, as the mailbox does: a sign-out asked for earlier would run ahead of the fresh-install check and the launch restore. The two windows' controllers know of each other only through `SettingsAppSignOutActivity`, and three things depend on it or stand beside it. Sign Out… asks nothing while the mailbox window has a sheet attached, with Settings in front too (`MailboxWindowSheet`, read in `SignOutMenuAction.perform`): the focused window is then the Settings window, and a sign-out confirmed there closed New Message on the mailbox with the typed message in it. Sign Out… is disabled in both windows while either one's sign-out runs (`SettingsAppSignOutController.isAnySignOutRunning`), and whether it can be chosen is decided in `SignOutMenuAction.init` and nowhere else, for the menu command and the button alike. And the Settings window can be closed while its sign-out runs, so a failure is then shown on the mailbox window: the Settings view tells its controller how to ask whether its window is on screen (`MacWindowVisibilityProbe`), and `ContentView`'s controller is the one made with `showsFailuresOfOffScreenWindows: true`. The command asks through `SettingsAppSignOutController.requestSignOut`, the controller that judges the iOS Settings switch, but stores no request (a stored one outlives a force quit and is picked up by a second window), and it asks nothing, and beeps, while the focused window has a sheet attached, where its alert would wait unseen (`SignOutMenuPolicy`). The New Message command follows the same rule (`MailboxMenuPolicy`, `MailboxMenuActions.chooseNewMessage`), and so must any menu command that presents a sheet: a window with a sheet attached takes no clicks, but a menu command and its shortcut still arrive, and the second sheet would wait behind the first. All of this was measured with a throwaway Mac program; none of it has been seen in the app.
- The Mac's mailbox is `MacMailboxView` (`MailboxRootView` picks it; iOS keeps the list in a `NavigationStack`): `MacConversationSidebar` beside a chat column, and the open chat is the sidebar's one selected row (`MacSidebarSelectionPolicy`; `docs/mac-imessage-ui-plan.md`). Four things follow from a chat that is a selection, not a pushed screen. A chat there must never call `dismiss()`: nothing was pushed, so it closes the window, and the Mac app is one `Window` scene, which quits when its window closes. `ChatView` closes itself only through `exitChat()`, which takes the presenter's `onExit` first (`ChatViewExitTests`). Selecting a row marks it read (`ChatMessagesCoordinator.handleAppear`), so nothing selects a row for the user at launch or when a conversation leaves by itself; only the user's own Archive or Report Spam on the list moves the selection to the next row. A selected chat stays on screen behind other apps, so `ChatView.isChatActiveAndUncovered` also asks whether the window appears active (`WindowAppearsActive`); drop that term and mail arriving in the background is marked read unseen. The sidebar's selection is its own, not `ConversationSelectionService.selectedConversationIDs`: `publishVisibleItems` prunes that set to the visible rows, so bound to it, typing in the search field would close the open chat. Batch actions go through `archiveConversations(withIDs:)` / `reportSpamConversations(withIDs:)`, each call under its own task key, because Delete pressed on row after row must not cancel the batch before it. The Mailbox menu's Mark as Read / Mark as Unread (Command-Shift-U, `MailboxCommands`) acts on `MacSidebarSelectionPolicy.readStateTargets`: the one selected conversation even while a search hides its row, because it is the open chat, or the selected rows the list shows. All of them go one way (`MailboxMenuPolicy.readStateCommand`: read if any is unread), and which way is decided again when the command is chosen (`ConversationListViewModel.changeReadState`), never taken from the title the menu last drew. `MailboxCommandsMenuTests` reads the item from the test host's real menu bar; the command has not been chosen in the app. A row of the sidebar's list is identified by a `MacSidebarRowID`, a struct holding the conversation's object ID, never by the `NSManagedObjectID` itself: a Mac list identified by object IDs (or `NSUUID`, or `NSString`) draws rows at the positions they had before once a single row has moved, while the table's own rows stay right, so a click opens another chat than the row shows. The first native build did exactly that on screen after its first sync (build 528, 2026-11-12); the list's selection is converted at the list's edge (`rowSelection`), and the mailbox's stays a set of object IDs. A probe of a Mac list must give the `ForEach` the row and nothing around it, identify the rows as the app does, and move a row: an `if`/`else` around the row hides the fault, which is how the probes written to find it missed it for hours (`MacConversationSidebarRowIdentityTests` draws the real sidebar's table and compares it with a freshly mounted one; CI runs only `MacConversationSidebarSourceTests`' pin of the row id). `MacMailboxDetail` is `Equatable` on the selection so the list's publishes (every search keystroke) do not re-evaluate the open transcript; keep anything it stores either fixed for the mailbox's life or a closure that reads state when called. The sidebar must also stay on screen, because nothing in the window or the menus reopens it. `macSplitViewColumnCannotCollapse()` on the sidebar column turns off its split view item's AppKit `canCollapse`, so the divider stops at the column's minimum width, and holds it off with an observation, because SwiftUI turns it back on at every update (`MacSidebarCollapseGuardView`). The `columnVisibility` reset is only the fallback behind it (`MacSidebarVisibilityPolicy`): alone, it closed and reopened the sidebar on nearly every event of a drag held past the point where the sidebar closes, and left the window wider. Keep `navigationSplitViewColumnWidth` the sidebar column's last modifier: with `toolbar(removing:)` applied after it the width is ignored and the sidebar comes up 144 points wide with a 140-point minimum (`MacMailboxViewSourceTests`). All three were measured in a throwaway program; none has been seen in the app. The sidebar also draws its own selection (`MacSidebarRowSelectionPolicy`): a Mac list shows its selection in the accent color only while the list has the keyboard focus, so with the caret in the reply field the open chat's row would be gray. The row's fill (`listRowBackground`) and its colors (`ConversationRowPalette`) come from one decision and go together (`MacConversationSidebarSourceTests`): white text on the list's own gray cannot be read. The fill is the only selection drawn: a `MacSidebarListSelectionGuardView` finds the `NSTableView` behind the list and sets its `selectionHighlightStyle` to `.none`, so the fill's shape does not have to match a selection underneath it, whose shape was measured on macOS 27.2 only. That write is not a flag. It reloads the table, so where and when it is made matters, and two things go together. The sidebar has a guard behind its list (the `background` of the `List`), which turns the selection off as the sidebar opens, with no row selected and the rows yet to load. And no guard writes from `layout()` or from any other call AppKit or SwiftUI makes into it: it leaves the write to the next turn of the main queue. The guard was first only in a selected row's fill and wrote from its `layout()`, so the reload came at the first click on a row, inside SwiftUI's drawing of that row: in a split view SwiftUI logged "NSHostingView is being laid out reentrantly" there every time, and on a list of 220 rows or more AppKit logged "reentrant operation in its NSTableView delegate. This warning will become an assert in the future". A turn later is not enough by itself: on a list that long the reload gets AppKit's warning from wherever it is made, which is why it is made before the rows are there. Keep the guard in the fill as well, for a list with none behind it. Two bounds on the guard are deliberate. A turn that finds no table looks again a few times over about three seconds, then waits for the list's next call (`standardLaterLookDelays`): the guard behind the list has no size, so nothing owes it the second `layout()` that found the table in the measurements. And one table's style is written `tableWriteLimit` times and no more, so a system whose table does not keep `.none` cannot reload the table at every turn; keep that count on the table, because the guard in a fill is a new view after every reload and a count of its own would start again each time. Where neither finds a table (nothing was run on macOS 26) the list's own selection is still drawn under the fill, which is why the fill keeps the list's shape and is square where selected rows touch (`MacSidebarRowSelectionPolicy.joins`). `MacConversationSidebarSelectionGuardTests` and `MacSidebarRowSelectionBackgroundTests` mount real lists in the Mac plan to pin that the table is found, from behind the list before any row is selected and from the fill, and `MacSidebarListSelectionGuardViewTests` that nothing is written inside a layout pass; CI runs only `MacConversationSidebarSourceTests`' pin that the list has the guard behind it. What the list then draws, and that the first selection logs neither message, was measured in throwaway programs and in the test host, not seen in the app. A probe for a message like those needs the list where the app has it: with the list alone in its window, and not in a split view, SwiftUI's fault was never logged. A row that is not selected gets no background view (`MacSidebarRowSelectionBackground.init` returns nil). A color the row draws must come from its palette, because a list never changes a color a row names; that includes the disc and the rings of a group's avatar (`GroupAvatarColors`), which `AvatarStackView` takes from the row. `ConversationRowView` takes `ConversationRowMetrics` (`.iOS` or `.mac`) as a required argument; `.iOS` is pinned field by field, and a change to the row is checked by drawing the iOS row before and after it. The chat's header is a value too: `ChatView` takes a required `ChatHeaderStyle`, and the Mac's is Messages' (`ChatHeaderPolicy`): the avatar as the toolbar's principal item and the name in a capsule in a `safeAreaBar` on the transcript (`MacChatHeaderNameBar`). Three things about it fail silently. The bar's height is part of the transcript's top inset, so it is one number for every chat from the moment the chat mounts: never make it follow the name, or come and go with anything that loads. The avatar's toolbar item is taken off the toolbar's glass (`macSharedBackgroundHidden`), and the capsule's offset is the number for an item without it, 0.5 points; with the glass the toolbar centers the item 2.5 points right of the column's center, so change the two together (`ChatHeaderStyleSourceTests`). And the capsule stays more than 20 points from the chat column's edges (`ChatHeaderMetrics.nameBarHorizontalPadding`): drawn off screen, a glass capsule nearer than that took the transcript under it out of the drawing a moment after it mounted. An off-screen drawing shows no glass and cannot be trusted for the color of anything on glass. Measured in the test host; none of it has been seen in the app.
- The chat's transcript is a value as well: `ChatView` takes a required `MessageBubbleStyle`, `.standard` on iOS and `.mac` in the Mac's chat column (`docs/mac-imessage-ui-plan.md`, PR 4). `.standard` is pinned value by value (`MessageBubbleStyleTests`), and a change to the bubble is checked by drawing the iOS chat before and after it. Four things about the Mac's style fail silently, all of them a row changing height after it mounts, which the transcript's reveal and anchoring cannot absorb. The time line is drawn inside the row it stands above (`ChatTranscriptRowLeadIn`), never as a row of the `ForEach`, and its modifier branches on the style only, so a line coming or going does not remount the bubble and its view model. It is decided from the row before, read past the window's edge (`rowForGrouping`), and only for a style with time lines: on iOS that read would be a fetch per row for nothing (`ChatBubbleStyleSourceTests`). The "Sent" caption has no timestamp line to share on the Mac, so the row reserves a line for it (`MessageSendStatusLinePolicy.reservesCaptionLine`): keep the line there for as long as a caption could come or go, and keep the row-wide status animation off in that arrangement, because it would animate the line leaving and with it the transcript's content size. The tail is drawn outside the bubble's frame, with the room for it kept by the row (`MessageBubbleStyle.bubbleTailWidth`), so a tail arriving or leaving moves nothing; `BubbleShape` fills the union of the bubble and the tail, because as two subpaths their overlap filled as a hole. And an image's width on the Mac is a fixed number, not a share of the window (`imageMaxWidth`): the image reserves its frame at mount. It is less only where the chat column is too narrow for that number (`imageMaxWidth(transcriptWidth:)`, under 496 points), where a row holding a 400-point image was cut off at both edges. Drawn in the test host; none of it has been seen in the app.
- The chat's composer is a value too: `ChatView` takes a required `ChatComposerStyle`, `.bar` on iOS and `.floating(.mac)` in the Mac's chat column (`ChatComposerPolicy`; `docs/mac-imessage-ui-plan.md`, PR 5). In both it is the overlay whose measured height is the transcript's bottom inset: never move it to a `safeAreaBar` or `safeAreaInset` (`ChatComposerStyleSourceTests`). Four things about the Mac's composer fail silently. Return sends mail, so what each key does is one pure function, `ReplyFieldKeyPolicy`, asked by the field's `NSTextView` delegate: never send over marked text, on a key repeat, or when `canSend` says no, and never give the field an `onKeyPress` or a second route to `onSend` (every send, from the button, the arrow and Return, goes through `ChatReplyBar.sendIfAllowed`). The field is an `NSTextView`, not a `TextField`, because a `TextField` submits on Shift-Return and selects the whole draft after a refused send. `FocusState` does not reach it, so its focus goes through `ReplyFieldFocusBridge`, and a chat reads and writes focus only through `ChatComposerFocus.wrappedValue`: a bare `isTextFieldFocused = false` in `ChatView` leaves the Mac's caret where it was. While an input method is composing a word the view is ahead of the composer by that word, so `applyTextFromComposer` leaves the view alone then unless the composer's text was replaced from outside (`composerTextKnownToField`), when the composer's text wins and the composition goes; and the send arrow has the field commit the word before it sends (`ReplyFieldFocusBridge.commitPendingInput`). Without the first the mail just sent came back as a draft, and without the second the reply went without its last word. The field also keeps its own undo manager (`undoManager(for:)`): a text view's default is its window's, and emptying that after a send emptied the search field's history too. A chat focuses its field when it appears unless a key selected its row (`focusesFieldWhenChatAppears`): focusing on every selection would stop the sidebar's arrow keys after one row and send the next Delete to the field instead of archiving the next conversation. And the field's fill is opaque and only the "+" button is glass: a wide glass shape over the transcript is what removed the transcript from PR 3's off-screen drawings. A `cacheDisplay` drawing puts a tick at each end of a stroked capsule; `ImageRenderer` does not. Drawn in the test host; none of it has been seen in the app.
- A file dropped on the Mac's chat is attached to its reply (`docs/mac-app-plan.md`, "Files"). `ChatView` puts one AppKit drop view behind the whole chat (`macDraftFileDrop`, `MacDraftFileDropView`), not a SwiftUI `dropDestination`: AppKit gives a drag to the frontmost view under the pointer that takes it, and two kinds of view in the chat do. The reply field's text view types a dropped file's path into the draft, and a `WKWebView` loads a dropped file in place of its page, with `hitTest` returning nil and its drag types unregistered alike. So `MacReplyTextView` and `LayoutAwareWKWebView` override the `NSDraggingDestination` methods and hand a file drag to the drop view under the pointer (`MacFileDropForwarder`), which a private SwiftUI destination could not be handed. The web view refuses every other drag and never calls `super`'s: keep it so, or a drop can replace an email with a file. Give any new AppKit view in the chat that takes drags the same forwarder. A drop goes through the Files picker's import and is refused wherever that picker's button is disabled (`DraftFileDropPolicy`): the composer has one `isProcessingAttachments` flag, which each import turns off as it ends, so two imports at once would enable Send over the second one's placeholder. A drop the chat took is the composer's `pendingFileDrop` until the picker starts on it, and it is only ever cleared by being imported: the composer takes no second drop while one waits, and a picker that hears of one while an import runs keeps it and starts when that import ends (`DraftFileDropPolicy.startsImport`). AppKit was told the drop was taken, so a request cleared any other way is files that left the pointer and were never attached. The drop view asks the pasteboard what a drag carries once for each drag, kept under the drag's sequence number. A dropped file opens no security scope (`startAccessingSecurityScopedResource()` answers false for it in the sandbox), so a drop's import passes `SecurityScope.ifOffered`; the pickers keep `.required`. The New Message and Forward sheet takes no drop. Measured in the test host with stand-in drags (`FakeDraggingInfo`); no file has been dropped in the app.
- A right-click on an attachment in the Mac's chat opens the attachment's own menu, with Save Attachment… and Save All Attachments… (`MacAttachmentExportMenu`; `docs/mac-app-plan.md`, "Files"). It is on the attachment's view, not in the message's menu, because only the bubble knows which attachments it shows; a view's own context menu replaces the one around it, so the row hands its own entries down (`macEnclosingMessageMenu`, `MacEnclosingMessageMenu`) and the attachment's menu ends with them: without that a message that is only a photo has no Reply or Forward in any menu. Give any other view in the row that gets a context menu of its own the same ending. Three rules. The name a save offers is the sender's and untrusted: it goes through `AttachmentExportPolicy.filename`, which drops paths, control and direction characters and leading dots, and the file's name on disk is never offered. That function works on Unicode scalars and must never go back to `Character`s: a `/` or a leading `.` followed by a combining scalar is one `Character` that is neither, and a split on `Character`s let a sender's name place a file in a subfolder. What counts as a name's extension has one definition, `AttachmentExportPolicy.splitExtension` (short, no space, not all digits), and the extension added to a name without one is its type's, never the stored file's, which the download takes from the sender's name. A save takes the attachment's own file (`AttachmentExportItem`, through `readableLocalURLValue`) and never the preview Quick Look falls back to. Save All replaces nothing in the folder the user chose (`AttachmentFileExport.saveAll`), and Save Attachment… never removes the file it replaces before the new copy is whole (`replaceItemAt`). The panels are AppKit's, behind closures on `MacAttachmentExporter`, so the tests never show one. The menu was read from the hosting view in the test host (`NSHostingView.menu(for:)`); no panel has been shown and nothing has been seen in the app.
- An attachment in the Mac's chat that has its file can be dragged out, as a file promise under that same cleaned name (`MacAttachmentFilePromiseProvider`): the stored file's URL would arrive in the Finder under its storage name, and a renamed copy in the container would be account data that sign-out does not know about. The drag source is an AppKit view over the attachment (`MacAttachmentDragSourceView`, `View.macAttachmentDragSource`), not `onDrag`, and three things go with it. It takes the left mouse button, so it hands a click on to the attachment's Quick Look and is only over an attachment that `isReady`: put it over a failed one and the retry control is unreachable. It is put there when the row is drawn, so its `hitTest` asks again at every press and answers nil once the attachment has lost its file. It is applied before `macAttachmentExportMenu`, so the menu's view contains it and its `menu(for:)` finds the attachment's menu behind it. And its dragging session is started through `beginSession`, which every test replaces: never start a real session in a test, it is the window server's and follows the user's pointer. Drops are allowed outside the app only. Measured in the test host with events handed to the view; no drag has been made in the app.
- Mac behaviors that are decisions, not gaps to close (Kevin, 2026-11-11; `docs/mac-app-plan.md`, decisions 5 to 8). Closing the window quits the app, so do not make the `Window` scene a `WindowGroup` or add a delegate that keeps the app running. SwiftUI quits an app whose one `Window` closes, but not while the Settings window is open (measured in a stand-in program: it ran on with only Settings), so `MacAppDelegate` also quits when the window whose identifier is `MacMainWindowPolicy.windowID` closes (`MacMainWindowCloseObserver`). That quit is asked for from the run loop (`perform(_:with:afterDelay:)`), never from `DispatchQueue.main.async` or a `Task`: `applicationShouldTerminate` holds a quit for a send in flight and answers from a main-actor task, and `terminate(_:)` called from a main-queue block waits inside it for an answer the queue can then never run, which hung the stand-in for good (`MacSettingsSceneSourceTests`). The first click in an inactive window only activates it: `LayoutAwareWKWebView` does not override `acceptsFirstMouse(for:)`, so that click cannot follow a link in the reader. A new install starts with about five minutes of mail, as on iOS, and nothing loads older mail. Compose has no From: alias picker on either platform.
- Deliberate asymmetries not to "fix": `AttachmentCacheActor` does not bump its generation on memory-pressure `clearCache(level:)`; `AuthSession.reopenHTMLContent` closes `CacheCoordinator` first even at cold launch.
